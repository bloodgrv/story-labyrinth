### P0 — fix first: silent corruption / broken data-integrity guarantees ✅ ALL FIXED 2026-08-19
These are the ones where the app actively lies to the user (reports success when it didn't work) or destroys/garbles their actual content. Everything else is either honestly broken (annoying but discoverable) or cosmetic.

1. **B15 — chat text silently splices into chapter manuscript prose.** ✅ **Fixed.** Root cause: three background `editor.update()` calls (grammar-check marks, RAG-issue-highlight marks, beat-accept marks) relocated the live Lexical selection/DOM focus into the chapter whenever they ran, regardless of where the user was actually typing (e.g. the chat composer). Fixed by tagging all three with `SKIP_DOM_SELECTION_TAG` and restoring the prior selection afterward ([useGrammarChecker.ts](../src/components/story-editor/plugins/GrammarCheckPlugin/useGrammarChecker.ts), [RagIssueHighlightPlugin/index.tsx](../src/components/story-editor/plugins/RagIssueHighlightPlugin/index.tsx), [BeatMarkSyncPlugin.tsx](../src/components/story-editor/plugins/BeatMarkSyncPlugin.tsx)), plus making the chat composer reclaim focus after a disabled/blur cycle and on chat switch ([MessageInputArea.tsx](../src/features/brainstorm/components/MessageInputArea.tsx)). Verified via `tsc --noEmit` and oxlint clean; live browser smoke-test showed no new console errors.
2. **B1 + B20 — same root cause, two entry points.** ✅ **Fixed.** Root cause: the chat layer's `modify_entry` proposal required the LLM to supply a real database `entryId` it had no legitimate way to know, causing either a false "success" against a hallucinated stub entry (B1) or an honest refusal (B20). Fixed by adding an `entryName` field the server resolves against the story's actual lorebook (reusing `resolveEntityIdsByName`, exported from [ragScanner.ts](../server/services/ragScanner.ts)) with a single-match substring fallback, updating the system prompt to ask for a name instead of an id ([chatContextService.ts](../server/services/chatContextService.ts)), and relaxing client-side parsing/types to accept either field ([parseCodexProposals.ts](../src/features/chat/services/parseCodexProposals.ts), [chats.ts](../server/routes/chats.ts)). Also fixed the "Unknown entry" label by invalidating lorebook queries on proposal creation ([useCodexProposalsQuery.ts](../src/features/chat/hooks/useCodexProposalsQuery.ts)). Verified via `tsc --noEmit` clean.
3. **B2 — Codex History restore partially reverts an entry.** ✅ **Fixed** (two independent root causes found and fixed). (a) The Core Identity/Appearance "add field" inputs kept typed label/value text in local React state that was only committed on Enter-in-the-value-field or the Add button — Enter in the *label* field had no handler and fell through to the surrounding form's implicit submit, silently saving the entry without the field ever being added. Fixed by giving the label input the same `onKeyDown` handler ([codexStateBoxes.tsx](../src/features/lorebook/components/form/codexStateBoxes.tsx)). (b) Separately, a real restore bug: the earliest snapshot of any entry (taken before Codex was ever filled in) has `codexState: null`, and restoring it wrote that `null` straight over the live entry's Codex column instead of an explicit empty state — restore now falls back to `EMPTY_CODEX_STATE` ([codexService.ts](../server/services/codexService.ts)), and the History panel now badges such snapshots "Empty state" with a clearer confirm-dialog warning ([CodexHistoryPanel.tsx](../src/features/lorebook/components/form/CodexHistoryPanel.tsx)). Verified live in browser against the QA session's own "Mara Ellison" entry — the "Empty state" badge renders correctly on her null-codexState snapshot.

### P1 — fix next: core propose→approve pipeline is unreliable or unreachable
This is the app's architectural center per CLAUDE.md ("Codex modifications require explicit user approval," propose-never-silently-write doctrine everywhere). These bugs mean that doctrine doesn't actually hold up end-to-end yet.

4. **B3 + B16 — Brainstorm structured-fence output cluster.** ✅ **Fixed 2026-08-19.** Two independent root causes, not one: (a) **B3** — no inline card component existed at all for `overview-proposal`/`handoff-packet`; `handleOverviewProposal`/`handleHandoffPackets` persisted to the server but never set React state for the per-message render loop to key off. Added `OverviewProposalCard.tsx` and `HandoffPacketCard.tsx`, message-keyed state in [ChatInterface.tsx](../src/features/chat/components/ChatInterface.tsx), and extracted the tray's accept/open logic into a shared [useBrainstormChecklistActions.ts](../src/features/brainstorm/hooks/useBrainstormChecklistActions.ts) hook so both the inline card and the Approvals tray perform the identical action. (b) **B16** — the automatic extraction pass's gate (`useChatMessageGeneration.ts`) skipped handoff extraction entirely whenever the reply had already self-emitted an overview-proposal fence (`!overviewProposal && handoffPackets.length === 0`); split into an either/or condition so either type missing triggers extraction, with a guard against double-applying whichever type was already present. Also added failure-vs-empty-result instrumentation to `brainstormExtractService.ts` (a real call failure now logs and surfaces a distinct toast instead of looking identical to "nothing to hand off"), and fixed the manual "Propose from this reply" retry to pass the preceding user message as context (it previously omitted it, so a user's own escalating "please make a real proposal" instructions were invisible to the extractor). **Verified live**: sent a message asking to lock in the synopsis — got both a "Synopsis" card with a working Accept button (wrote the story's synopsis, marked the setup slot known, moved the checklist item to "opened", logged a transfer) AND a "Proposes 6 hand-offs" card in the same reply, something the old gate could never have produced together. Console clean throughout.
5. **B6 — character-name hallucination in Brainstorm and Editor Chat.** ✅ **Fixed 2026-08-19 — real grounding gap, not a prompting problem.** Root cause: character context only ever reached the model via RAG-ranked search (`resolveCodexEntries` in [chatContextService.ts](../server/services/chatContextService.ts), capped at `RELEVANT_ENTRIES_LIMIT = 8`, filtered by semantic similarity to the current turn). No comprehensive "these are the only real characters" list existed anywhere in the prompt, so any character not semantically close to the current message was invisible to the model — exactly reproducing QA's "invented several new incidental deceased characters including a near-duplicate of an established name." Fixed by adding `resolveCharacterRoster` — a full, deterministic (not RAG-ranked, names-only) list of the story's character-category Lorebook entries, scoped by the same global/story/series conditions [aiReviewService.ts](../server/services/aiReviewService.ts)'s `resolveCastForChapters` already established — surfaced as a new `[ESTABLISHED CAST ...]` block in `computeExtraContext`, refetched fresh every turn (same staleness class already fixed once for B18's outline tree, not the older mount-time snapshot), for Editor/WorldBuilding/Outline (always) and Brainstorm (when its own `includeLorebook` toggle is on) — reusing the existing "is lorebook in scope for this chat" boolean rather than a new toggle. The block instructs the model never to present an unlisted name as established. This is grounding, not enforcement — reduces but can't 100% guarantee zero hallucination — but the model now has the information it was missing. `tsc --noEmit` clean.
6. **B18 — Outline chat's edit path appends duplicates instead of editing in place.** ✅ **Fixed 2026-08-19.** Root cause: the `[OUTLINE TREE — ...]` context block (containing the real item ids the model needs to emit an `edit` fence) was built ONCE at chat-mount time and never rebuilt for the rest of the conversation — its effect's dependency array had nothing that changes when outline items are created/accepted/rejected. On a chat opened against an empty outline it said "(empty)" for the entire session even after 20 items existed, leaving the model with no ids to reference, so it could only fall back to `create` fences reconstructing chapters from titles still visible in the transcript — exactly the reported duplicate-chapter append. The `edit`/`reorder`/`delete` fence types and their parser/routing were already correct and unaffected. Fixed by moving the outline-tree block into [ChatInterface.tsx](../src/features/chat/components/ChatInterface.tsx)'s `computeExtraContext`, which already re-fetches real context on every turn (used by Research/Guide for the same reason) — extracted the formatting logic into a shared `formatOutlineTree` helper so the (now-removed) stale mount-time copy and the fresh per-turn one can never disagree, and added an explicit prompt instruction to use edit/reorder/delete for anything already in the tree rather than re-creating it. **Verified live**: asked to rename Chapter 1 and add a Chapter 4 scene — got a real `edit` proposal card ("Editing Carrier Hiss / Title → First Contact") plus one legitimate `create` (the new scene), accepting the edit fired `PUT /api/outline/:id → 200` and renamed the chapter in place with zero duplicate chapters created (still exactly 5).
7. **B19 — Editor Chat composer can get permanently stuck** (zero requests fire, no error) when chat focus and the active chapter tab disagree. ✅ **Fixed 2026-08-19.** Two co-occurring, independently-fixed defects. (1) The real silent no-op: `generate()`'s single combined guard (`useChatMessageGeneration.ts`) bailed with zero feedback whenever `selectedModel` resolved to `null` — invisible because the Send button's `disabled` check never looked at it. Root cause: `resolveChatDefaultModel`/`resolveModelForModeSwitch` ([resolveChatDefaultModel.ts](../src/features/ai/utils/resolveChatDefaultModel.ts)) returned a model id straight out of AI settings with no validation against the actual catalogue — a stale default, rotated key, or unreachable local server could name a model that no longer exists, and that bad id then got *persisted* to the chat row, so the dead state survived reloads and only "New Chat" (which starts with no persisted id) escaped it. Fixed by validating the fallback against `availableModels` before returning/persisting it, adding explicit error toasts for the "no prompt"/"no model" cases, and mirroring the guard in the Send button's own `disabled` state so it's never clickable-but-dead. (2) The reported chapter-focus mismatch itself: switching chapters via the tab strip updated `currentChapterId` but never re-pointed `selectedEditorChat` at the new chapter — [StoryEditor.tsx](../src/features/chapters/components/StoryEditor.tsx) now clears the selected chat on a genuine chapter change, forcing a resync so "Focused on" can never contradict the active tab. **Verified live**: sent a message in a fresh Editor chat, confirmed `POST /messages → 201` with a resolved model, clean console.
8. **B17 — "Suggest relationships" AI job completes but produces zero output** on an obvious, relationship-rich cast. ✅ **Fixed 2026-08-19.** Same root-cause family as B16: `graph_suggest_edges` ([graphSuggestEdgesJob.ts](../server/services/jobs/graphSuggestEdgesJob.ts)) sent `max_tokens: 2048` to the LLM, and a 10-entry cast with real relationships easily produces 15-25 proposed edges — enough JSON to truncate mid-object, throw in `JSON.parse`, and silently degrade to an empty array with **zero logging anywhere in the six different silent-empty paths** (no `[...]` match, parse failure, per-item shape rejection, bad index, invalid edge type, already-existing edge) — completely indistinguishable in the job's "completed" status from "the model genuinely found nothing." Raised the budget to match B16's fix, added `finish_reason === "length"` truncation detection, wrapped the LLM call to fail the job loudly instead of swallowing errors, and added logging at every branch that can produce zero results. Also applied the same `max_tokens` raise + logging to `timelineSuggestPinsJob.ts`, flagged by the investigation as a byte-for-byte copy of the identical bug (relevant to B10's data loss too). **Verified live**: "Suggest relationships" on the QA session's 10-entry Lorebook now produces 3 real, well-reasoned pending edges (Mara Ellison --works_at--> WKLR 870 AM Station, Mara Ellison --owns--> Mara's Cassette Log, plus a genuinely useful `alias_of` catch on a duplicate "Mara Ellison" entry left over from earlier testing) — confirmed via the raw `/graph/pending` response, not just the UI badge.
9. **B5 — "New version" (alternate chapter draft) button fires zero requests.** ✅ **Fixed 2026-08-19 — turned out to be a false positive with a real underlying fragility.** The wiring itself was intact; live reproduction showed the button was an icon-only Radix `DropdownMenuTrigger`, which opens on `pointerdown` rather than `click` — a synthetic click that only dispatches mouse events (not full pointer events) never opens it, reproducing "zero requests" exactly. Not a fix-nothing situation though: the trigger's only label was an HTML `title` tooltip (invisible until hover), and the adjacent `AddTabMenu`'s "+" has the identical anonymous-icon shape ~40px away, easy to conflate. Replaced the 2-item dropdown with two always-visible, plainly-`onClick` buttons ("New version" / "Duplicate") in [ChapterVersionsPanel.tsx](../src/features/chapter-versions/components/ChapterVersionsPanel.tsx), and gave `AddTabMenu`'s trigger a visible "Add tab" label in [AddTabMenu.tsx](../src/features/editor-multiview/components/AddTabMenu.tsx). **Verified live**: "New version" opens the Generate dialog, "Duplicate" fires `POST /api/chapters/:id/versions → 201 Created`. Worth flagging for future QA passes: any "button does nothing, zero requests" finding on an icon-only dropdown trigger should be re-verified with real pointer events, not just a plain click — the currently-open **B10** (Timeline "Accept all") may be worth a second look through this lens.

### P2 — real bugs, narrower blast radius
10. **B21 + B14 — primary-action buttons need 2-3 clicks with no feedback, across Create Story, New Entry, New Chat template picks, Approvals Accept/Close, and chat Send.** ✅ **Resolved 2026-08-19** — turned out to be a grab-bag of unrelated things wearing the same symptom, not one shared root cause: one real, now-fixed code bug (WB "New Chat" template items), one real fix from the earlier pass (chat Send), and the rest — Create Story, Approvals Close, and B14 (New Entry) — all cleared as non-reproducing once retested with the Browser pane actually composited; the first attempt at those three produced misleading failures from the pane itself, not the app (see below):

During that gap the Send button stayed fully idle-looking: not disabled, icon unchanged, composer text uncleared — indistinguishable from a click that never registered, and with no re-entrancy guard a second click during that window re-ran the whole send path concurrently. Fixed with a synchronous `isSubmittingRef` guard (state alone lags a render behind a same-tick second click) plus an `isSubmitting` state that feeds the composer's `isGenerating` prop so it flips to its "Stop" rendering the instant Send is clicked, not once `generate()` begins. **Verified live**: typed a message, fired two rapid clicks at the Send button (one native, one via a second synchronous `.click()` in the same tick to remove any timing luck) — exactly one exchange landed (confirmed via the chat's own message list, not just a toast), composer cleared and re-armed correctly, console clean. A real single-click send was re-verified working normally afterward.
    - **Create Story dialog. ✅ Re-verified, no defect — closed out.** Retested 2026-08-19 with the Browser pane actually composited (a real, visible browser, not the non-compositing automation state used for the first pass — see WB "New Chat" note below for why that distinction turned out to matter). On a clean page load, a single real pointer click on "Create New Story" opened the dialog correctly every time, confirmed via the dialog's own `data-state="open"`. No code defect; the original finding doesn't reproduce against a real click.
    - **WB "New Chat" template-picker dropdown items. ✅ Real bug found and fixed 2026-08-19 — not a testing artifact after all.** Re-investigated with a properly composited browser (the earlier "likely same testing-artifact class as B5" guess was itself based on a non-compositing session where CSS animations never completed, which turned out to make *everything* look broken — see below). Waiting ~1s between opening the menu and clicking made the same click succeed, confirming a race rather than a permanently broken handler. Fixed by switching to Radix's own `onSelect` (the primitive's purpose-built, more robustly-sequenced selection event, decoupled from the generic bubbled click) — **verified live**: reproduced the exact original failing timing (open, click immediately, zero wait) post-fix and the click now reliably registers, the menu closes immediately, and the new chat opens once its creation request resolves. `tsc --noEmit` clean. No guard/gate found in `openNewEntryTab` ([LorebookPage.tsx](../src/features/lorebook/pages/LorebookPage.tsx)) that could explain a dropped first click either.

That produced misleading failures unrelated to any app code; re-running the same tests with the pane genuinely visible resolved them.
11. **B10 — Timeline "Accept all" partial data loss** (reports more successes than pins that actually land). ✅ **Fixed 2026-08-19.** Root cause: `ensureSpineTimeline` ([storyTimelineService.ts](../server/services/storyTimelineService.ts)) is a plain select-then-insert get-or-create with no atomicity guard. "Accept all" fires N concurrent `createPin` requests (one per pin, no `timelineId`), each of which independently resolves the story's spine timeline — under real concurrency, more than one request's select can see "no spine yet" before any insert lands, so multiple spine timeline rows get created and the pins' memberships split across them. The board only displays whichever spine row a later `ensureSpineTimeline` call happens to resolve to, so pins attached to the "losing" spine silently vanish from view even though their creation genuinely succeeded (hence the toast/board-count mismatch). Fixed with a partial unique index (`storytimelines_unique_spine_idx` on `storyId WHERE isDefault = 1`, migration `0079_thin_wolfsbane.sql`) plus a catch-and-reselect fallback in `ensureSpineTimeline` so a losing concurrent insert re-fetches the winning row instead of throwing or orphaning data — mirrors the already-verified-working partial index pattern on `storyGraphEdges` (see `DECISIONS.md`). **Verified**: confirmed via `PRAGMA index_list`/`index_xinfo` that the index is a genuine partial index (not silently widened by drizzle-kit), then reproduced the race directly against `createPin` with 5 concurrent calls — the pre-fix code threw `SQLITE_CONSTRAINT_UNIQUE` deterministically once the index existed (proving the race is real), and the fixed code produced exactly 1 spine timeline with all 5 pins as members, every time. `tsc --noEmit` and the full vitest suite (92 tests) stay clean.
12. **B8 — Relationship Graph drag-to-connect silently repositions nodes instead of connecting them when zoomed out.** ✅ **Fixed 2026-08-19.** Root cause: xyflow's connection handles ([StoryGraphNode.tsx](../src/features/story-graph/components/StoryGraphNode.tsx)) used the library default `min-width/height: 5px`, invisible (`opacity-0`) permanently — and being ordinary DOM descendants of the zoom-transformed canvas, their real on-screen hit size shrinks right along with node size as the canvas zooms out. At 100% that's already tight; at the reported ~58px-node zoom it's small enough that a drag starting even a few pixels off the handle's true center lands on the pane (or node) instead, silently panning/moving rather than connecting — with no visual cue, since the handle was invisible even on approach, so the miss looks like intended behavior. Also confirmed xyflow's `connectionRadius` prop (default 20, [StoryGraphCanvas.tsx](../src/features/story-graph/components/StoryGraphCanvas.tsx)) only governs snapping to the *target* handle once a drag is already in progress — it doesn't help the *starting* handle, which strictly requires a literal hit on its own DOM element. Fixed with a much larger explicit hit-size (5px → 14px) and `group-hover:opacity-100` so the handle is visible — and discoverable — right when a user approaches it, plus a raised `connectionRadius={40}` for the target-snap side of the gesture. **Verified live** with a rigorous pre/post comparison at the exact reported zoom level (~0.67, ~40px rendered nodes): a drag offset by a fixed few pixels from the handle's exact center reproducibly missed and panned the canvas against the original 5px handle (`elementFromPoint` at the drag start resolved to `react-flow__pane`, no dialog), then — with the identical offset, same zoom, same nodes, only the fix restored — correctly landed on the handle and opened the "New Relationship" dialog pre-filled "From Mara Ellison To Dale Kreeger". `tsc --noEmit` and the full vitest suite (92 tests) stay clean.

Fixed by updating `CLAUDE.md`'s UX Flow section and correcting both stale comments to point at Settings > Scanner and cite the real commit. 16. **B11 — recurring React console errors** (max update depth, hydration mismatch, controlled/uncontrolled input). ✅ **All 3 of 3 fixed and verified 2026-08-19.**

""}` (not a real model id, so it just keeps the placeholder showing until resolved, controlled from the first render). **Verified live**: reproduced the warning naturally 4 times pre-fix (opening chat panels across Editor/WB/Research/Outline during normal navigation); after the fix landed (HMR), opening fresh chat panels across Editor/Brainstorm/Outline produced zero new occurrences.

The captured stack pointed at [StoryGraphCanvas.tsx](../src/features/story-graph/components/StoryGraphCanvas.tsx)'s layout `useEffect` (the one calling `setFlowNodes`/`setFlowEdges`). Root cause: `displayedNodes`/`displayedEdges` were plain `const` ternaries, not memoized — `neighborhoodQuery.data?.nodes ?? []` builds a brand-new `[]` reference on every single render whenever `neighborhoodQuery.data` is undefined (ego view, query disabled/data-less e.g. right as `centerEntryId` resolves or during unmount), which reran the effect every render, which called `setFlowNodes([])`/`setFlowEdges([])` with yet another new-reference empty array, triggering another render — a genuine unbounded loop, not a rare timing race, that just happened to only get *noticed* during a tool switch since that's when the "brief window of no data" condition was most likely to hold. Fixed by wrapping both in `useMemo` keyed on their real underlying data. **Verified live**: reproduced the exact original failing sequence with a stack-capturing listener installed (0 errors → confirmed pre-fix stack originates in the layout effect), applied the fix, then re-ran a *more* aggressive version of the original repro (multiple full Relations→Maps→Timeline→AI Review→Brainstorm cycles, rapid-fire, no delays) — zero errors, every time. Also confirmed the graph still renders and functions correctly post-fix (ego view showing a real node on a story with actual Lorebook entries). `tsc --noEmit` clean; full vitest suite (92 tests) stays clean.
17. **B12 — two unexplained, unisolated 500s in console.** ⚠️ **Still not reproduced after three separate investigation passes (2026-08-19); the underlying two 500s remain genuinely unconfirmed, but each pass has closed off a real gap in how well the app's error-visibility can be trusted.** Pass 1's core claim — "every genuine 500 is unconditionally logged as `Server error:` regardless of which route file handles it" — turned out to be **false**. Checked directly: 8 of the 10 route files with a local `asyncHandler` ([ai.ts](../server/routes/ai.ts), [autoHumanizer.ts](../server/routes/autoHumanizer.ts), [grammar.ts](../server/routes/grammar.ts), [humanizer.ts](../server/routes/humanizer.ts), [tts.ts](../server/routes/tts.ts), [series.ts](../server/routes/series.ts), [chats.ts](../server/routes/chats.ts) — the single highest-traffic route in the app — and [codex.ts](../server/routes/codex.ts)) catch their own errors, send `res.status(500)` themselves, and **never reach** `server/index.ts`'s global error middleware at all — so a genuine 500 from any of them was logged under a route-specific label instead (`"Error:"`, `"Chat error:"`, `"Codex error:"`, ...), completely invisible to a `preview_logs { search: "Server error" }` sweep. **Fixed** by consolidating all 8 duplicated local `asyncHandler` definitions into one shared [server/lib/asyncHandler.ts](../server/lib/asyncHandler.ts), logging under the exact same `"Server error:"` prefix the global middleware uses. (`auth.ts`/`users.ts`'s local handlers were deliberately left alone — they return 400 for validation errors, a different, intentional posture.) Pass 1 also did a live sweep (rapid cross-tool navigation during in-flight chat generation) — zero 500s, but did accidentally reproduce B11's "Maximum update depth exceeded" once, non-deterministically at the time (later root-caused and fixed for good, see B11). Pass 2 (this session, later) ran the broadest sweep yet — every sidebar tool across two different stories, RAG Scanner (real scan run), Humanizer (real rewrite), Names generator, Series create/delete (including deliberately adversarial input: emoji, quotes, angle brackets in the name, to rule out an unescaped-input crash), agent jobs, codex endpoints, Settings' every sub-tab (Logs/Data/Trash/Scanner/Users) — roughly 250 requests inspected directly, all 200/201, plus both a `"Server error"` and a bare `"500"` search against the live server log, both empty. TTS and grammar-check specifically weren't exercisable (both disabled by default in this dev environment, TTS renders nothing when off, grammar-check never fires a request) — the one real coverage gap left, not a place a 500 was ruled out, just untested. Given three passes now (increasing in thoroughness each time) with zero reproductions and a QA source that never tied it to a specific action either, further blind sweeping isn't a good use of effort — leaving this open as "genuinely can't reproduce, but any future occurrence is now uniformly greppable via `Server error:`," rather than continuing to chase it without a lead.

- **B4 — "Rework in chat" (Notes).** ✅ **Independently reconfirmed working 2026-08-19.** Ran the full flow twice end-to-end on a fresh note: create note → type body → "Rework in chat" → open Chat rail → "Reworking selection" panel appears with the note's title/content captured correctly → talk through a change → model proposes an updated version in a card → "Save note" → `PUT /api/notes/:id → 200` with the correct merged content. - **New bug found and fixed while reconfirming B4 — Notes editor showed stale content after "Rework in chat" saved an update.** The rework flow's "Save note" (in `NotesChatRail.tsx`) correctly persisted the new content to the server every time, but the still-open `NoteEditor.tsx` pane kept showing the pre-rework text — confirmed via the raw PUT response (`content` updated correctly server-side) vs. the visibly stale WYSIWYG box next to it. Root cause was two compounding issues: (1) [NoteEditor.tsx](../src/features/notes/components/NoteEditor.tsx)'s `content`/`title` are local `useState`, seeded once from the note query and never resynced when the note changes via a sibling component's mutation (the chat rail, not the editor itself); (2) the notes PUT route ([server/routes/notes.ts](../server/routes/notes.ts)) never actually set `updatedAt` on update at all — only on create — so even a resync keyed on `note.updatedAt` would never have fired, and the "Last updated" timestamp shown in the editor was silently frozen at creation time forever regardless of how many times a note was saved. Fixed both: the PUT route now always sets `updatedAt: new Date()` (client-supplied value ignored, mirroring the POST route's existing convention), and `NoteEditorContent` now has a `useEffect` that resyncs local `content`/`title` whenever `note.id` or `note.updatedAt` changes. **Verified live**: ran two full rework→Save note cycles without ever navigating away — the editor pane's text and "Last updated" timestamp both updated immediately in place on the second cycle (post-fix), where the first cycle (pre-fix, pre-server-restart) had shown genuinely stale content and an unchanged timestamp despite a correct server-side save. `tsc --noEmit` clean.
