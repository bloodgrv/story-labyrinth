## Suggested fix priority

This re-ranks the flat severity labels below by actual risk and clusters bugs that likely share one root cause, so a fix in one place may resolve several IDs at once. Sections below (Blocker/Major/Minor) are left in their original QA-report grouping and IDs are untouched — this is a triage lens on top, not a renumbering.

### P0 — fix first: silent corruption / broken data-integrity guarantees ✅ ALL FIXED 2026-08-19
These are the ones where the app actively lies to the user (reports success when it didn't work) or destroys/garbles their actual content. Everything else is either honestly broken (annoying but discoverable) or cosmetic.

1. **B15 — chat text silently splices into chapter manuscript prose.** ✅ **Fixed.** Root cause: three background `editor.update()` calls (grammar-check marks, RAG-issue-highlight marks, beat-accept marks) relocated the live Lexical selection/DOM focus into the chapter whenever they ran, regardless of where the user was actually typing (e.g. the chat composer). Fixed by tagging all three with `SKIP_DOM_SELECTION_TAG` and restoring the prior selection afterward ([useGrammarChecker.ts](../src/components/story-editor/plugins/GrammarCheckPlugin/useGrammarChecker.ts), [RagIssueHighlightPlugin/index.tsx](../src/components/story-editor/plugins/RagIssueHighlightPlugin/index.tsx), [BeatMarkSyncPlugin.tsx](../src/components/story-editor/plugins/BeatMarkSyncPlugin.tsx)), plus making the chat composer reclaim focus after a disabled/blur cycle and on chat switch ([MessageInputArea.tsx](../src/features/brainstorm/components/MessageInputArea.tsx)). Verified via `tsc --noEmit` and oxlint clean; live browser smoke-test showed no new console errors.
2. **B1 + B20 — same root cause, two entry points.** ✅ **Fixed.** Root cause: the chat layer's `modify_entry` proposal required the LLM to supply a real database `entryId` it had no legitimate way to know, causing either a false "success" against a hallucinated stub entry (B1) or an honest refusal (B20). Fixed by adding an `entryName` field the server resolves against the story's actual lorebook (reusing `resolveEntityIdsByName`, exported from [ragScanner.ts](../server/services/ragScanner.ts)) with a single-match substring fallback, updating the system prompt to ask for a name instead of an id ([chatContextService.ts](../server/services/chatContextService.ts)), and relaxing client-side parsing/types to accept either field ([parseCodexProposals.ts](../src/features/chat/services/parseCodexProposals.ts), [chats.ts](../server/routes/chats.ts)). Also fixed the "Unknown entry" label by invalidating lorebook queries on proposal creation ([useCodexProposalsQuery.ts](../src/features/chat/hooks/useCodexProposalsQuery.ts)). Verified via `tsc --noEmit` clean.
3. **B2 — Codex History restore partially reverts an entry.** ✅ **Fixed** (two independent root causes found and fixed). (a) The Core Identity/Appearance "add field" inputs kept typed label/value text in local React state that was only committed on Enter-in-the-value-field or the Add button — Enter in the *label* field had no handler and fell through to the surrounding form's implicit submit, silently saving the entry without the field ever being added. Fixed by giving the label input the same `onKeyDown` handler ([codexStateBoxes.tsx](../src/features/lorebook/components/form/codexStateBoxes.tsx)). (b) Separately, a real restore bug: the earliest snapshot of any entry (taken before Codex was ever filled in) has `codexState: null`, and restoring it wrote that `null` straight over the live entry's Codex column instead of an explicit empty state — restore now falls back to `EMPTY_CODEX_STATE` ([codexService.ts](../server/services/codexService.ts)), and the History panel now badges such snapshots "Empty state" with a clearer confirm-dialog warning ([CodexHistoryPanel.tsx](../src/features/lorebook/components/form/CodexHistoryPanel.tsx)). Verified live in browser against the QA session's own "Mara Ellison" entry — the "Empty state" badge renders correctly on her null-codexState snapshot.

### P1 — fix next: core propose→approve pipeline is unreliable or unreachable
This is the app's architectural center per CLAUDE.md ("Codex modifications require explicit user approval," propose-never-silently-write doctrine everywhere). These bugs mean that doctrine doesn't actually hold up end-to-end yet.

4. **B3 + B16 — Brainstorm structured-fence output cluster.** ✅ **Fixed 2026-08-19.** Two independent root causes, not one: (a) **B3** — no inline card component existed at all for `overview-proposal`/`handoff-packet`; `handleOverviewProposal`/`handleHandoffPackets` persisted to the server but never set React state for the per-message render loop to key off. Added `OverviewProposalCard.tsx` and `HandoffPacketCard.tsx`, message-keyed state in [ChatInterface.tsx](../src/features/chat/components/ChatInterface.tsx), and extracted the tray's accept/open logic into a shared [useBrainstormChecklistActions.ts](../src/features/brainstorm/hooks/useBrainstormChecklistActions.ts) hook so both the inline card and the Approvals tray perform the identical action. (b) **B16** — the automatic extraction pass's gate (`useChatMessageGeneration.ts`) skipped handoff extraction entirely whenever the reply had already self-emitted an overview-proposal fence (`!overviewProposal && handoffPackets.length === 0`); split into an either/or condition so either type missing triggers extraction, with a guard against double-applying whichever type was already present. Also added failure-vs-empty-result instrumentation to `brainstormExtractService.ts` (a real call failure now logs and surfaces a distinct toast instead of looking identical to "nothing to hand off"), and fixed the manual "Propose from this reply" retry to pass the preceding user message as context (it previously omitted it, so a user's own escalating "please make a real proposal" instructions were invisible to the extractor). **Verified live**: sent a message asking to lock in the synopsis — got both a "Synopsis" card with a working Accept button (wrote the story's synopsis, marked the setup slot known, moved the checklist item to "opened", logged a transfer) AND a "Proposes 6 hand-offs" card in the same reply, something the old gate could never have produced together. Console clean throughout.
5. **B6 — character-name hallucination in Brainstorm and Editor Chat.** Undercuts the "factual consistency / prevent drift" premise that's this fork's whole reason for existing. Priming ("use only established characters") helps but doesn't fully fix it — treat as a grounding/context-injection problem, not a prompting problem the user should have to work around.
6. **B18 — Outline chat's edit path appends duplicates instead of editing in place.** ✅ **Fixed 2026-08-19.** Root cause: the `[OUTLINE TREE — ...]` context block (containing the real item ids the model needs to emit an `edit` fence) was built ONCE at chat-mount time and never rebuilt for the rest of the conversation — its effect's dependency array had nothing that changes when outline items are created/accepted/rejected. On a chat opened against an empty outline it said "(empty)" for the entire session even after 20 items existed, leaving the model with no ids to reference, so it could only fall back to `create` fences reconstructing chapters from titles still visible in the transcript — exactly the reported duplicate-chapter append. The `edit`/`reorder`/`delete` fence types and their parser/routing were already correct and unaffected. Fixed by moving the outline-tree block into [ChatInterface.tsx](../src/features/chat/components/ChatInterface.tsx)'s `computeExtraContext`, which already re-fetches real context on every turn (used by Research/Guide for the same reason) — extracted the formatting logic into a shared `formatOutlineTree` helper so the (now-removed) stale mount-time copy and the fresh per-turn one can never disagree, and added an explicit prompt instruction to use edit/reorder/delete for anything already in the tree rather than re-creating it. **Verified live**: asked to rename Chapter 1 and add a Chapter 4 scene — got a real `edit` proposal card ("Editing Carrier Hiss / Title → First Contact") plus one legitimate `create` (the new scene), accepting the edit fired `PUT /api/outline/:id → 200` and renamed the chapter in place with zero duplicate chapters created (still exactly 5).
7. **B19 — Editor Chat composer can get permanently stuck** (zero requests fire, no error) when chat focus and the active chapter tab disagree. ✅ **Fixed 2026-08-19.** Two co-occurring, independently-fixed defects. (1) The real silent no-op: `generate()`'s single combined guard (`useChatMessageGeneration.ts`) bailed with zero feedback whenever `selectedModel` resolved to `null` — invisible because the Send button's `disabled` check never looked at it. Root cause: `resolveChatDefaultModel`/`resolveModelForModeSwitch` ([resolveChatDefaultModel.ts](../src/features/ai/utils/resolveChatDefaultModel.ts)) returned a model id straight out of AI settings with no validation against the actual catalogue — a stale default, rotated key, or unreachable local server could name a model that no longer exists, and that bad id then got *persisted* to the chat row, so the dead state survived reloads and only "New Chat" (which starts with no persisted id) escaped it. Fixed by validating the fallback against `availableModels` before returning/persisting it, adding explicit error toasts for the "no prompt"/"no model" cases, and mirroring the guard in the Send button's own `disabled` state so it's never clickable-but-dead. (2) The reported chapter-focus mismatch itself: switching chapters via the tab strip updated `currentChapterId` but never re-pointed `selectedEditorChat` at the new chapter — [StoryEditor.tsx](../src/features/chapters/components/StoryEditor.tsx) now clears the selected chat on a genuine chapter change, forcing a resync so "Focused on" can never contradict the active tab. **Verified live**: sent a message in a fresh Editor chat, confirmed `POST /messages → 201` with a resolved model, clean console.
8. **B17 — "Suggest relationships" AI job completes but produces zero output** on an obvious, relationship-rich cast. ✅ **Fixed 2026-08-19.** Same root-cause family as B16: `graph_suggest_edges` ([graphSuggestEdgesJob.ts](../server/services/jobs/graphSuggestEdgesJob.ts)) sent `max_tokens: 2048` to the LLM, and a 10-entry cast with real relationships easily produces 15-25 proposed edges — enough JSON to truncate mid-object, throw in `JSON.parse`, and silently degrade to an empty array with **zero logging anywhere in the six different silent-empty paths** (no `[...]` match, parse failure, per-item shape rejection, bad index, invalid edge type, already-existing edge) — completely indistinguishable in the job's "completed" status from "the model genuinely found nothing." Raised the budget to match B16's fix, added `finish_reason === "length"` truncation detection, wrapped the LLM call to fail the job loudly instead of swallowing errors, and added logging at every branch that can produce zero results. Also applied the same `max_tokens` raise + logging to `timelineSuggestPinsJob.ts`, flagged by the investigation as a byte-for-byte copy of the identical bug (relevant to B10's data loss too). **Verified live**: "Suggest relationships" on the QA session's 10-entry Lorebook now produces 3 real, well-reasoned pending edges (Mara Ellison --works_at--> WKLR 870 AM Station, Mara Ellison --owns--> Mara's Cassette Log, plus a genuinely useful `alias_of` catch on a duplicate "Mara Ellison" entry left over from earlier testing) — confirmed via the raw `/graph/pending` response, not just the UI badge.
9. **B5 — "New version" (alternate chapter draft) button fires zero requests.** ✅ **Fixed 2026-08-19 — turned out to be a false positive with a real underlying fragility.** The wiring itself was intact; live reproduction showed the button was an icon-only Radix `DropdownMenuTrigger`, which opens on `pointerdown` rather than `click` — a synthetic click that only dispatches mouse events (not full pointer events) never opens it, reproducing "zero requests" exactly. Not a fix-nothing situation though: the trigger's only label was an HTML `title` tooltip (invisible until hover), and the adjacent `AddTabMenu`'s "+" has the identical anonymous-icon shape ~40px away, easy to conflate. Replaced the 2-item dropdown with two always-visible, plainly-`onClick` buttons ("New version" / "Duplicate") in [ChapterVersionsPanel.tsx](../src/features/chapter-versions/components/ChapterVersionsPanel.tsx), and gave `AddTabMenu`'s trigger a visible "Add tab" label in [AddTabMenu.tsx](../src/features/editor-multiview/components/AddTabMenu.tsx). **Verified live**: "New version" opens the Generate dialog, "Duplicate" fires `POST /api/chapters/:id/versions → 201 Created`. Worth flagging for future QA passes: any "button does nothing, zero requests" finding on an icon-only dropdown trigger should be re-verified with real pointer events, not just a plain click — the currently-open **B10** (Timeline "Accept all") may be worth a second look through this lens.
