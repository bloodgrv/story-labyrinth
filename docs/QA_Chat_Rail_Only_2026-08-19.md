# QA: Chat-Rail-Only Pass — 2026-08-19

**Tester:** Claude (agent), driving the app via browser automation
**Story used:** "The Static Choir" (psychological horror, radio-station premise), a fresh story — not "The Glasswing Heist" from the prior pass
**AI provider:** Grok 4.5 (xAI), cloud — used throughout, worked without needing any Feature Routing troubleshooting
**Method:** Chat-rail-only. Every piece of content (story premise, 5 characters, 3 locations, 2 items, outline, timeline pins, notes, 5 chapters) was created through chat propose→approve flows. The only manual-form fallbacks were: setting a Lorebook entry's Category dropdown to Location/Item after creating it via chat-adjacent quick-create (the WB chat template picker doesn't set category itself), and clicking Accept/Reject/Approve buttons on rendered proposal cards (which is the intended UI, not a "manual form" bypass). Both are logged explicitly below where they occurred.

## Summary

The chat propose→approve pipeline is visibly more mature than the prior (mixed manual/chat) pass suggested in a few places — **B4 (Notes "Rework in chat") is now fully fixed**, sheet-proposal/place-sheet-proposal/note-proposal/psych-proposal cards render and Accept correctly essentially every time, "Accept All Suggestions" on the Outline works cleanly, and the character-hallucination problem (B6) is much better when the chat is explicitly primed with "use only established characters." AI Review's Deep mode is genuinely excellent and caught a real continuity bug (a live/dead status contradiction on Ruth Alvarez, plus the Krieger/Kreeger near-duplicate name) with no prompting from me.

However, this pass surfaced a cluster of **new, more serious problems concentrated in exactly the areas CLAUDE.md identifies as architecturally central**: the Brainstorm `handoff-packet` fence is essentially non-functional (three escalating attempts, zero landed in Approvals — worse than the previously-documented `overview-proposal` rendering bug, because the underlying data doesn't even get captured), the "AI-suggested relationships" job silently produces zero suggestions despite an obvious cast with clear relationships, the Timeline "Accept all" is now a *partial*-loss bug rather than a *total*-loss b; the Outline chat's "edit an existing chapter" path frequently misfires into "append a duplicate copy of the whole outline" instead; and — most seriously — **chat text can silently land inside the manuscript body instead of the chat composer**, corrupting chapter prose with zero warning. B1 (Codex-update entry resolution) still reproduces, though in a less destructive form than before: this time the model refuses rather than silently overwriting, but it's the same underlying entry-resolution defect.

Chat-vs-form effort was mixed: WB Character/Locations sheet-proposals are now genuinely *faster* than filling the Advanced panel by hand (one message, one Accept & Sync click, done). But Brainstorm handoffs, Timeline batch-accept, and Outline single-chapter edits are all currently *slower and less reliable* via chat than the equivalent manual action would be — you end up needing 2-4 retries and still can't fully trust the result without manually verifying the underlying data.

## New Bugs

1. **Handoff-packet proposals are effectively unreachable via natural Brainstorm chat.**
   - *Repro:* In a Brainstorm chat with an accepted `overview-proposal` already on record, ask "send a handoff-packet to World-Building for [two characters]." Then, when nothing shows up in Approvals, explicitly say "that wasn't captured as a real handoff-packet, use the actual fenced format." Then, as a third attempt, literally spell out the exact backtick-fence syntax to use (` ```handoff-packet `) and what JSON fields to include.
   - *Expected:* At least one of the three escalating attempts produces a real, Approvals-visible handoff card.
   - *Actual:* Attempt 1 produced plain prose with a "Handoff Packet →" markdown header (not a fence). Attempt 2 produced a YAML-ish `to:`/`story:`/`canon_summary:` block, still not a real parsed fence. Attempt 3 (exact syntax spelled out) produced a monospace code-block rendering (so *something* about it registered as "code"), but the Approvals dialog's "Handoffs" section — both Active and Done tabs — stayed at "No active handoffs" / "No done handoffs" throughout, while a *duplicate* `overview-proposal` synopsis card appeared in the Active tab instead, unprompted. The underlying handoff mechanism appears to never fire correctly through organic conversation.
   - *Severity:* Major. *Phase:* 2 (Brainstorm).

2. **"Suggest relationships" (AI-suggested graph edges) job completes but produces zero suggestions despite an obvious cast.**
   - *Repro:* With 5 characters, 3 locations, and 2 items in the Lorebook (clear relationships: Mara works at WKLR, Dale manages WKLR, Mara owns the Cassette Log, etc.), open Relations → click "Suggest relationships."
   - *Expected:* At least a handful of pending edges appear in the Pending tab, or a visible error/empty-result explanation.
   - *Actual:* Settings → Logs → Recent Jobs shows "Relationship suggestions — completed" (no failure), but the Pending tab shows "No pending suggestions" both immediately and ~30s later. No edges of any kind were produced from an 10-entry Lorebook with obvious relationships. This means the *only* practical way to populate the Relationship Graph is still manual drag-to-connect, confirming and extending the prior pass's finding that chat/AI-driven edge creation doesn't work in practice — this pass shows even the dedicated AI-suggest *job* (not chat) silently fails to produce anything.
   - *Severity:* Major. *Phase:* WB / Relations.

3. **Outline chat "edit an existing chapter" request gets misinterpreted as "append duplicate chapters" instead of editing in place.**
   - *Repro:* After accepting an initial 5-chapter/20-item outline via "Accept All Suggestions," ask the Outline chat: "Please rename Chapter 1 to 'Carrier Hiss' → 'First Contact' and add one more scene beat to Chapter 4 about George finding Dale's hidden tapes. Propose the edit so I can accept it."
   - *Expected:* A small, targeted proposal that renames Chapter 1's title and adds one scene card to Chapter 4.
   - *Actual:* The model instead generated five entirely new AI-suggested chapters (6 through 10 — "First Contact," "Sale and Ash," "False Mourning," "The Living Conductor," reusing/duplicating titles and content from the existing outline) appended after the original 5, effectively doubling the outline instead of editing it. Chapter 1's title was untouched ("Carrier Hiss" unchanged) and Chapter 4 got no new scene. "Reject All Suggestions" cleanly removed the erroneous batch, so no permanent damage, but the *editing* use case (as opposed to *initial generation*) does not work as expected.
   - *Severity:* Major (the outline chat's initial-generation path is solid; its edit/iterate path is not, which cuts against the "conversational, iterative" design intent). *Phase:* 2 (Outline).

4. **Chat composer text can silently land inside the chapter manuscript body instead of the chat panel, corrupting prose with no warning.**
   - *Repro:* In the Editor, with a chapter open and its chat panel visible, click into what should be the chat composer and type a message, then send. Observed once, reproducibly-risky: after switching between two different Editor Chats for the same chapter (an existing chat vs. a freshly-created one) and clicking through several UI states (chat list panel → back to composer), a typed chat message ("Please emit an actual shuttle-proposal so I can open it in Research, not just a text note saying you'd flag it.") appeared **spliced mid-word into the chapter's prose text itself** — inserted directly into the manuscript between "his mothe" and "r's hand" in an existing sentence, with no proposal card, no chat bubble, and no confirmation dialog.
   - *Expected:* Chat input always lands in the chat composer, never in the document body, regardless of prior UI navigation.
   - *Actual:* Silent content corruption. Caught only because the word count and visible chapter text were being actively cross-checked; a normal user proofreading later would find garbled, out-of-place text mid-sentence with no indication of what happened or when. Recovered with a single Ctrl+Z (undo), confirming the editor's own undo stack absorbed it as a normal edit — meaning nothing in the app itself flagged this as anomalous.
   - *Severity:* Blocker (silent data/content corruption in the user's actual manuscript — the single most damaging class of bug this pass found). *Phase:* 3 (Editor Chat / chapter chats).

5. **Editor Chat composer can get stuck fully non-responsive (message never posts, no error) even across a full page reload, tied to stale/mismatched chapter-chat focus.**
   - *Repro:* In the Editor with multiple chapter tabs open, switch between chapters via the tab strip while a chat panel is showing a *different* chapter's chat (visible as "Focused on: Chapter: Live Conductor" while the active editor tab is "Carrier Hiss"). Type a message and click Send.
   - *Expected:* Either the message sends against the correctly-focused chapter's chat, or the composer visibly refuses/clarifies which chapter it's about to message.
   - *Actual:* Multiple send attempts (4+, across different click targets and even a keyboard Enter) produced zero `POST .../messages` network calls — confirmed via network-request inspection, not just visual — while the UI gave no error, spinner, or disabled state. This persisted after a full page reload and after retrying in what looked like a previously-working chat. Only fully resolved by explicitly opening "New Chat" from the chat list and re-selecting a chat via the list UI (not the chapter tab) to force focus resync.
   - *Severity:* Major (silent total failure with no error surfaced; only detectable via devtools-level network inspection). *Phase:* 3 (Editor Chat).

6. **"Suggest a Codex update" one-shot action produces an unhelpful/incorrect "no existing entry" claim for an already-Codex-tracked character.**
   - *Repro:* In the Editor Chat for Chapter 1 (a chapter that opens by mentioning Mara Ellison, an existing, fully Codex-populated Lorebook entry created earlier in the same session), click the composer's one-shot "Suggest a Codex update for Mara" action (surfaced automatically after selecting/mentioning her name).
   - *Expected:* The chat resolves Mara Ellison's existing entry (she has a populated Core Identity, Wardrobe, Wounds, Items, etc. already) and proposes a real diff against it.
   - *Actual:* "There's no existing Mara entry available to this chat, so I can't safely send a modify_entry — inventing or guessing the id would break the update... paste Mara's existing entry ID line from her Lorebook card into the chat, and I'll propose the exact edit." The chat has no way to resolve an obviously-referenced, already-existing character to her real entry without the user manually pasting an internal ID — which no ordinary user would know how to find. This is the same root defect as B1 (entry resolution from prose context), surfaced through a different, purpose-built entry point that should have been more reliable, not less.
   - *Severity:* Major. *Phase:* 3 (Editor Chat / Codex updates).

7. **Story/chapter/entity creation buttons frequently require 2-3 clicks with zero visible feedback on the first 1-2 clicks (broader than previously-documented B14).**
   - *Repro:* "Create Story" dialog: fill Title/Author, click "Create Story." Repeat if nothing happens.
   - *Expected:* First click creates the resource (or shows a validation error).
   - *Actual:* Reproduced on "Create Story" specifically — first two clicks on "Create Story" fired **zero** network requests (confirmed via network log), no error, no loading state, dialog just sat there; the third click finally fired the real `POST /api/stories` and succeeded. This is a broader pattern than the previously-logged B14 (Lorebook "New Entry" needing 2 clicks) — it affects the top-level Create Story flow too, and in this case took 3 attempts rather than 2. Also reproduced repeatedly on WB "New Chat" template-selection dropdown items, Approvals "Accept"/"Close" buttons, and chat Send buttons throughout every phase of this pass (dozens of instances, consistent with the prior pass's friction #2, but now confirmed severe enough to also block real actions, not just delay them).
   - *Severity:* Major (this is a broad, structural issue across nearly every primary-action button in the app, not a one-off). *Phase:* throughout.

## New Friction

1. **WB chat sheet-proposal → Accept & Sync → Codex-tray Approve is genuinely fast and pleasant — faster than the manual form.** Creating a fully-populated character (Core Identity, Physical Appearance, Wardrobe, Wounds, Items) took one chat message + two clicks (Accept & Sync, then Approve in the Pending Codex tray) versus the many individual field entries the Advanced panel form would require. This is the one clear case this pass where chat effort was *lower* than form effort — worth highlighting since the task specifically asked for this comparison.

2. **Creating a Location or Item entry via chat still requires a manual Category-dropdown fix first.** The "New Entry" flow defaults every new entry to Category=Character regardless of which WB template you're about to use (Character Codex / Locations & Settings / Freeform). To create a Location via chat, you still have to open Advanced, manually flip Category from Character to Location, *then* start the WB chat — otherwise the Lore Sheet template that loads doesn't match what you're building. This is a small but real manual-form dependency baked into an otherwise chat-first flow, and it's easy to miss (the WB chat proceeds fine even with the wrong category selected, silently producing a location's content inside a "Character" entry).

3. **Editor Chat panel silently drops/resets its context when navigating away and back**, even mid-task. After accepting a Codex sync on a character page, then returning to check the codex-pending-changes tray, the chat panel reset to "Pick a template to start a focused world-building session" — losing the just-used conversation from view (though the underlying data persisted fine; this is a navigation/state-retention issue, not data loss). This happened repeatedly across the WB, Editor, and Notes chat surfaces and forced re-opening "New Chat" or hunting through the chat list to resume.

4. **The Names Generator's Codex quick-add sets a permanent "Needs fleshing out — generated by the Name Generator" tag that never auto-clears**, even after the entry is subsequently fully fleshed out via a WB chat sheet-proposal (confirmed: George Williams' Lorebook card still showed the stub tag after his full sheet, Codex sync, and psych profile were all accepted). Minor but a real "tidiness" gap — a user would have to remember to manually clear this tag.

5. **Timeline "Suggest pins" (bulk AI-propose) and Relations "Suggest relationships" both fire from a single ambiguous icon** in the tool's top-right icon rail with no visible label until clicked (confirmed via the resulting toast text, not the icon itself) — a user exploring the UI cold would have no way to know that icon starts an AI job versus, say, opening a settings panel. Both of these AI-suggest entry points are easy to miss and, per bugs #2 above, one of them (Relations) doesn't reliably produce anything anyway.

6. **Long AI Review Deep-mode runs give staged progress text ("Cross-chapter pass...", "Voice pass...", "Review complete.") which is good — but this is inconsistent with most other long-running AI actions in the app** (Brainstorm/WB/Outline/Editor chat sends, Relations "Suggest relationships," Timeline "Suggest pins") which give zero progress indication beyond a possible stuck-looking "Generating (Xs)" counter that itself sometimes appears to reset/stall (observed jumping from 44s back down during a WB chat generation, suggesting the timer itself may not be reliable). AI Review's staged-progress pattern should arguably be the app-wide standard.

## Notes for whoever triages this

- The single most important finding this pass is **new Bug #4** (chat text silently landing in manuscript prose) — it's the only finding that represents actual, silent corruption of the user's creative work product with zero recovery path other than noticing the garbled text and knowing to Ctrl+Z. Everything else in this report is either "the feature doesn't do what it claims" (bad, but discoverable) or "the feature needs a retry" (annoying, but safe). This one is neither.
- B1's persistence across two QA passes, in two different trigger surfaces (RAG-Scanner-drawer-adjacent free text in the first pass, Editor-Chat-composer and one-shot-action in this pass), strongly suggests the underlying defect is in how the chat context resolves "a character mentioned in prose" to "an actual Lorebook entry ID" — not a surface-specific bug. Worth investigating as a single root-cause fix rather than patching each entry point separately.
- B3's extension to `handoff-packet` (new Bug #1) suggests the entire family of Brainstorm-chat structured-fence outputs may share a common weakness: the model reliably produces *some* recognizable structured output (an `overview-proposal`, a JSON-ish blob, a monospace block) but doesn't reliably hit the *exact* fence-name/format the server-side parser is keyed on. Worth checking whether the system prompt's fence-format instructions are being included/weighted correctly for `handoff-packet` specifically, since `overview-proposal` at least reaches the Approvals tray reliably while `handoff-packet` never does.
