# DECISIONS.md — Story Nexus Fork

Architecture decisions that are not obvious from the code or CLAUDE.md.

---

## AI Client Factory

**Decision:** All server-side LLM calls go through `server/services/aiClientFactory.ts` (`buildClientForFeature`), not inline `new OpenAI(...)` calls.

**Rationale:** CLAUDE.md requires per-feature endpoint selection (writing model on one machine, scanner model on another). The factory encapsulates the two-level resolution:
1. Per-feature override from `aiSettings.featureEndpoints` (if configured)
2. Global defaults: local → openai → openrouter (existing priority order)

**How to add a new feature:** Add its key to `FeatureKey` in `src/types/aiSettings.ts` and `FEATURE_LABELS`/`FEATURE_KEYS`, then call `buildClientForFeature("your_feature_key")`.

---

## Feature Endpoints Storage

**Decision:** Per-feature endpoint config is stored as a JSON column (`featureEndpoints`) on the single `aiSettings` row, not in a separate table.

**Rationale:** `aiSettings` is a global, single-row settings table. Adding a join table for per-feature overrides would add complexity with no benefit — the factory always loads the full settings row anyway. JSON-in-column keeps it in one place.

---

## Pending Change Flow for New Codex Entries

**Decision:** When a chat proposes a new Codex entry, a stub `lorebookEntry` is created immediately (with `needsFleshingOut: true`), then the `codexPendingChange` is created against that stub.

**Rationale:** `codexPendingChanges.entryId` is NOT NULL. The stub satisfies the FK constraint and makes the proposed entry immediately visible in the lorebook. On approval, the stub is filled in and `needsFleshingOut` is cleared. On rejection, the stub remains for manual attention.

---

## sourceRef Format

**Decision:** Chat-originated Codex pending changes use `sourceRef` values of the form:
- `chat:{chatId}` — when no specific message is known
- `chat:{chatId}:msg:{messageId}` — when traceable to a specific message

**Rationale:** Enables prefix-matching with `LIKE 'chat:{chatId}%'` to retrieve all proposals from a given chat, regardless of which message generated them.

---

## World-Building Chat Templates

**Decision:** Templates are a static catalogue in `src/types/worldbuilding.ts` (`WORLD_BUILDING_TEMPLATES`), not stored in the database.

**Rationale:** Templates define structural intent (system prompt hints, defaults), not user data. Storing them in code allows version control and avoids seed/migration overhead. User-created chats reference a `templateSlug` which resolves to the static catalogue at runtime.

---

## Vector RAG (sqlite-vec + FTS5)

**Decision:** Embeddings and keyword search live in two sqlite virtual tables created via raw SQL in migration `0009_rag_vector_search.sql`, joined back to a normal Drizzle-managed metadata table (`ragChunks`) by a shared `chunkId` (the chunk's UUID), not by matching sqlite rowids across tables.

- `vec_chunks` (sqlite-vec `vec0`): `storyId TEXT PARTITION KEY, embedding float[768], +chunkId TEXT`. The `PARTITION KEY` lets `WHERE storyId = ? AND embedding MATCH ? AND k = ?` pre-filter efficiently before the KNN search — plain auxiliary (`+`) columns cannot be used in a KNN query's `WHERE` clause, only partition key columns can.
- `fts_chunks` (FTS5): standalone table (`content, chunkId UNINDEXED, storyId UNINDEXED`), not an "external content" table. External-content FTS5 needs the content table's rowid to double as `content_rowid`, which doesn't fit `ragChunks`' text-UUID primary key without extra bookkeeping. A standalone table kept in sync manually by the repository layer is simpler and fully under our control.
- `server/db/client.ts` loads the `sqlite-vec` extension on the raw `better-sqlite3` connection *before* wrapping it with Drizzle and before `runMigrations()` executes, since `CREATE VIRTUAL TABLE ... USING vec0(...)` requires the extension to already be loaded.

**Embedding dimension is fixed at 768** (`EMBEDDING_DIMENSIONS` in `server/services/embeddingService.ts`), matching the `vec0` column declared in the migration. Switching to an embedding model with a different dimension requires a new migration that drops and recreates `vec_chunks`, plus a full re-embed — there is no runtime-configurable dimension in this phase.

**Search ranking:** `hybridSearch` (in `server/services/ragRepository.ts`) runs the FTS5 keyword query and the vec0 similarity query independently, then merges them with Reciprocal Rank Fusion (`1/(60 + rank)` per list, summed). If no embedding endpoint is configured (or the embedding call fails), `ragIndexService.search` catches the error and falls back to keyword-only search rather than failing the whole request.

**Feature endpoint:** embeddings use a new `"embedding"` `FeatureKey` (see `src/types/aiSettings.ts`), resolved through the existing `buildClientForFeature` factory. There is no separate fallback path — if the user hasn't configured an `embedding` override and the global default is a chat model, the `/embeddings` call will fail with a provider error, which is the signal to configure a dedicated embedding endpoint.

**Indexing scope:** only story-level lorebook entries (`level: "story"`) and chapters are indexed. Global/series-level lorebook entries are skipped for now because they can apply to multiple stories at once and `ragChunks`/`vec_chunks` are partitioned by a single `storyId` — indexing them properly would need a many-story association, deferred to a later phase.

**Integration is manual/pull-based, not hooked into existing CRUD routes.** `server/routes/rag.ts` exposes `POST /api/rag/index/lorebook/:entryId`, `POST /api/rag/index/chapter/:chapterId`, matching `DELETE` routes, `POST /api/rag/reindex/story/:storyId` (bulk backfill), and `POST /api/rag/search`. Wiring automatic reindex-on-save into the Codex/chapter CRUD routes, and building the RAG Scanner UI that consumes `/api/rag/search`, are follow-up work.

**Bug fixed while building this:** `server/services/ragIndexService.ts` originally re-`JSON.parse`'d `lorebookEntries.codexState` before indexing it. Drizzle's `text(..., { mode: "json" })` columns already deserialize to objects on `db.select()` (see `SQLiteTextJson.mapFromDriverValue` in `drizzle-orm`), so `JSON.parse(anObject)` was throwing and getting silently swallowed by the local try/catch — codex state was never actually included in indexed lorebook text. Fixed by using the already-parsed object directly. Follow the existing convention (`server/lib/json.ts`'s `parseJson`, which only parses when the value is actually a string) rather than assuming JSON columns need manual parsing.

## RAG Scanner (Factual Consistency Checker)

**Decision:** The scanner (`server/services/ragScanner.ts`) reuses `ragIndexService.search()` for retrieval — it does not talk to `vec_chunks`/`fts_chunks` directly. For a given chapter, its own text is chunked (`embeddingService.chunkText`) and each chunk is used as a separate search query (capped at 6 queries via even sampling for long chapters), merging/deduping the results by `chunkId` and excluding the chapter's own chunks so it can't "match itself." The top 15 merged chunks (by RRF score) become the LLM's reference context.

**Storage:** two new tables, `ragScans` (one row per scan run — either `scope: "chapter"` or `scope: "story"`) and `ragScanIssues` (individual findings, FK'd to a scan). This mirrors the `codexSnapshots`/`codexPendingChanges` pattern already in the codebase: a parent audit-trail row plus child detail rows, all non-destructive — issues are never deleted, only their `status` (`open` → `dismissed`/`resolved`) changes via `PATCH /api/rag/issues/:issueId`.

**Whole-story scans run in the background, not synchronously.** `POST /api/rag/scan/story/:storyId` resolves the AI connection and creates the `ragScans` row (`status: "running"`, `totalChapters` set) *before* returning, then processes chapters one at a time in a detached async function, updating `processedChapters` after each. There's no job queue in this codebase, so the client polls `GET /api/rag/scan/:scanId` for progress and the issues found so far. A single chapter's failure during a story scan is caught and logged per-chapter (`processedChapters` still advances) rather than aborting the whole run; only a failure outside that per-chapter try/catch marks the whole scan `status: "failed"`.

**The AI connection is resolved once up front**, not per chapter — `scanChapter`/`scanStory` call `buildClientForFeature("rag_scanner")` before creating the scan row (so an unconfigured scanner fails fast with a clean error, rather than creating a "running" scan doomed to fail on every chapter) and pass the resolved `{ client, model }` down into the per-chapter logic.

**Entity resolution:** the LLM is asked for a `relatedEntityName` (string) rather than an internal id, then resolved against a case-insensitive name → id map scoped to the story's visible lorebook entries (global + this story + this story's series — same scoping rule as `entityDetector.ts`'s existing entity lookup). Unmatched names resolve to `null` rather than failing the issue.

**Bug found and fixed while building this:** the `openai` npm client defaults `encoding_format` to `"base64"` on `embeddings.create()` when not explicitly set, then decodes the response client-side assuming it's base64. Local OpenAI-compatible servers (LM Studio, Ollama, etc.) commonly ignore `encoding_format` entirely and always return plain float arrays — the SDK was silently mis-decoding those as base64, corrupting every embedding (verified with a fake local server: a 768-float array came back as 192 floats). Fixed by passing `encoding_format: "float"` explicitly in `embeddingService.ts`. This would have silently broken embeddings for most local/self-hosted setups, which is the primary target deployment per CLAUDE.md.

**Verified end-to-end** with a fake local OpenAI-compatible server (embeddings + chat completions) standing in for a real provider: indexing → chapter scan → issue storage/filtering/entity-resolution → background story scan with progress polling → issue triage, all exercised against the real code path (not mocked internals).

## Chat System Enhancements (Template Injection, Codex Context, Proposal Revision)

**Template system prompts are assembled at request time, not stored in the chat's message history.** `ChatMessage.role` is `"user" | "assistant"` only (no `"system"`) — the codebase's existing convention is that system framing lives separately from the visible transcript (see `PromptMessage.role` including `"system"` for the Prompts feature, used to build LLM requests, while chat *history* stays a clean, user-editable transcript with edit metadata like `originalContent`/`edited`). Following that convention, `server/services/chatContextService.ts` computes `systemPrompt` (base framing + the chat's `templateSlug` → `systemPromptHint`, if any) fresh on each call to `GET /api/chats/:chatId/context`, rather than writing a fake system message into `aiChats.messages` at chat-creation time. A future chat UI (or `AIService` client-side) is expected to fetch this context and prepend it to the actual LLM request, the same way Prompts are assembled today.

**One context-assembly endpoint, not three.** `GET /api/chats/:chatId/context?query=...` returns `{ systemPrompt, pendingProposals, relevantCodexEntries }` together, since a chat needs all three at the same moment (right before generating a response or proposal) — `systemPrompt` satisfies template injection, `pendingProposals` reuses the already-existing `getChatCodexProposals` (filtered to `status: "pending"`), and `relevantCodexEntries` reuses the RAG hybrid search (`ragIndexService.search`) filtered to `entityType: "lorebook_entry"` results, using the chat's title as the query when none is supplied (so the endpoint is never empty on first load). This directly reuses the Vector RAG infrastructure rather than building a separate Codex-lookup path.

**Proposal revision reuses the existing pending-change row instead of a new table.** Added `revisePendingChange` (`codexRepository.ts`) and `reviseChatProposal`/`getChatProposal` (`chatCodexService.ts`): a chat can fetch a single proposal it made (`GET /api/chats/:chatId/codex-proposals/:pendingChangeId`) or revise its proposed fields in place while still `pending` (`PATCH` same route) — e.g. the conversation refines an earlier proposal before the user approves/rejects it, instead of creating a competing duplicate. Both are ownership-checked: a proposal only "belongs" to a chat if its `sourceRef` is `chat:{chatId}` or `chat:{chatId}:msg:{id}` (same prefix rule as `getPendingChangesByChatId`); a different chat gets a clear error, not silent cross-chat access. No new audit-trail row is created for a revision — the proposal hasn't taken effect yet, so there's nothing to snapshot until it's approved (at which point the existing `codexSnapshots` flow already records history).

**Verified end-to-end**, not just written: real DB + a fake local embeddings server exercising the actual code path — template hint appears/differs correctly per template, RAG search surfaces the right Codex entry as `relevantCodexEntries`, a proposal is visible via both `getChatCodexProposals` and `getChatContext`, cross-chat proposal access is rejected, revising in place doesn't create a duplicate, and revising an already-approved proposal correctly fails.

## Docker: glibc base image + build-time verification

**The `node:22-alpine` → `node:22-slim` switch (from the Vector RAG session) is necessary but not sufficient — it was never actually build-tested**, because `npm run build` was silently broken the whole time: `src/types/story.ts` imported `./codex` / `./worldbuilding` without `.js` extensions, which fails under the server tsconfig's `moduleResolution: "nodenext"`. Since `npm run build` is `tsc && tsc --project server/tsconfig.json && vite build` (chained with `&&`), the server tsc step exited non-zero and `vite build` never ran — `docker build` would have failed on `RUN npm run build`, before ever reaching the sqlite-vec question at all. This had been flagged as a "pre-existing, unrelated" typecheck error in every prior session's verification pass; it only became blocking once something actually tried to run the full build. Fixed by adding the missing `.js` extensions (two-line fix, `src/types/story.ts:1-2`).

**Build-time verification, not just a base-image swap.** Two scripts run as `RUN` steps in the Dockerfile itself, so a broken image can never be produced (the build fails, not the first request in production):
- `server/scripts/verify-sqlite-vec.mjs` — loads the extension in a throwaway `:memory:` DB, creates a real `vec0` table, inserts a vector, runs a KNN query. Runs in **both** stages: once in the builder (right after `npm ci`, before spending time on the rest of the build) and once in the production stage (after its own separate `npm ci --omit=dev`, since that's a distinct install of the platform binary and the image that actually ships).
- `server/scripts/verify-migrations.mjs` — runs the full migration chain against a scratch DB path using the *compiled* `dist/server/server/db/{migrate,client}.js` (not the TypeScript source), then explicitly checks that `ragChunks`/`ragScans`/`ragScanIssues` (regular tables) and `vec_chunks`/`fts_chunks` (virtual tables) all exist afterward. This is deliberately pickier than "migrations didn't throw" — it protects against the specific failure mode where a virtual table silently fails to materialize while the migration otherwise reports success. Scratch DB lives at `.migration-verify-scratch/` under the container's cwd and is always cleaned up (best-effort — a locked-file cleanup failure logs a warning but never masks the actual pass/fail result).
- `server/db/client.ts` also logs `sqlite-vec loaded (vX.Y.Z)` on every real boot (not just at build time), so a working extension is visible in `docker logs`/server startup output during normal operation too, not just at image-build time.

**Update: verified for real once Docker Desktop was installed.** `docker build -t storynexus-test .` succeeded end to end, and both verification gates passed inside the actual Debian glibc containers (not simulated): `verify-sqlite-vec.mjs` printed `extension loaded, version v0.1.9` + `vec0 virtual table + KNN query OK` in both the builder and production stages, and `verify-migrations.mjs` printed `full migration chain OK — ragChunks/ragScans/ragScanIssues/vec_chunks/fts_chunks all present`. Then ran the built image (`docker run`) and hit it over real HTTP: `sqlite-vec loaded (v0.1.9)` appears in `docker logs` at container startup, `/api/health` and `/api/auth/status` respond correctly, `/api/stories` 401s without a session and 200s with one after registering through `/api/auth/register`, and `POST /api/rag/search` returns `200 {"results":[]}` rather than crashing — confirming the sqlite-vec query path (`vec_chunks`/`fts_chunks`) executes correctly at real runtime, not just at build time. The glibc/musl concern that started this whole thread is fully resolved and confirmed, not just reasoned about.

**docker-compose files needed no changes.** All three (`docker-compose.yml`, `.dev.yml`, `.prod.yml`) use `wget` for healthchecks and `user: "${PUID:-1000}:${PGID:-1000}"` — both already accounted for in the Dockerfile from the earlier session (`apt-get install ... wget`; `node:22-slim` provides the same built-in `node` user, uid 1000, as the Alpine variant did).

## Basic Login & Password Protection

**Schema is a real `users` table, not a singleton config row**, even though this phase only supports one account — `aiSettings`-style singleton rows work when there's exactly one conceptual "thing" forever, but a user model that might later grow roles/multiple accounts shouldn't start as a blob to avoid a breaking migration later. `sessions` is a normal FK'd child table. Single-user scope is enforced at the *service* layer instead: `POST /api/auth/register` refuses with 403 once `getUserCount() > 0` — the schema doesn't know or care that it's single-user.

**Zero new dependencies.** Password hashing uses Node's built-in `crypto.scrypt` (OWASP-recommended KDF, N=2^17/r=8/p=1 — ~200-400ms per hash/verify, benchmarked locally) instead of bcrypt/argon2, both of which are native modules that would have reopened the exact glibc/musl Docker fragility this project just spent a whole session fixing. Cookie reading is a 10-line manual parser instead of `cookie-parser` (`res.cookie()` for *setting* cookies is already built into Express — only *reading* `req.headers.cookie` needed anything, and that's a two-line loop).

**Sessions are server-side and stored hashed, not JWTs.** The cookie holds a random 256-bit token; only `sha256(token)` is ever persisted (`server/services/authService.ts`'s `hashToken`) — mirrors why `passwordHash` isn't the raw password: a DB dump alone can't be replayed as a valid session. This also makes logout/revocation trivial (delete the row), which a stateless JWT wouldn't give without a denylist.

**Cookie `secure` flag defaults to `false`, opt-in via `COOKIE_SECURE=true`.** CLAUDE.md requires "Support remote access via Tailscale from work PC," and Tailscale/LAN access is typically plain HTTP with no TLS termination in front of it. Defaulting `secure: true` (the usual security-conscious default) would silently break login for this project's actual primary deployment target. `httpOnly` and `sameSite: "lax"` are always on regardless.

**Auth is applied globally to `/api/*`, not selectively to "sensitive" routes.** The task instructions suggested protecting "AI settings and Codex if needed" specifically, but `aiSettings` holds OpenAI/OpenRouter/Gemini API keys and the lorebook/chapters/prompts routes hold the actual creative content — protecting only two route groups while leaving the rest open on a LAN/Tailscale-exposed instance would be a false sense of security, not real security. `server/index.ts` mounts `/api/auth` and `/api/health` *before* a blanket `app.use("/api", requireAuth)`, so those two stay reachable while logged out and everything registered after requires a valid session — no per-route configuration to get wrong or forget.

**Login failures are rate-limited in-memory, not persisted**, and deliberately don't distinguish "unknown username" from "wrong password" (both return a generic 401; an unknown username still runs a throwaway `hashPassword` call so the response timing doesn't leak which case it was). 5 failed attempts locks that username for 15 minutes. This resets on server restart, which is an accepted tradeoff for a personal/local tool — it's defense-in-depth against casual brute force, not the only line of defense.

**Registration auto-logs-in.** The first-run "Create Account" flow immediately issues a session on success rather than requiring a second login step — there's no meaningful security reason to make someone log in again immediately after proving they just set the password.

**Frontend: a single `AuthGate` wrapping the whole app**, not per-route guards — checks `GET /api/auth/status` once on load and renders `LoginPage` (in either "create account" or "log in" mode, based on `setupComplete`) instead of the app when not authenticated. Also listens for a custom `auth:unauthorized` event that `apiFactory.ts` dispatches on any `401` response (excluding `/auth/*` itself), so a session that expires *mid-use* drops back to the login screen instead of every subsequent API call just silently failing.

**Verified end-to-end, in both an automated script and the real browser**: a Node script exercising the actual running server confirmed health/status work logged-out, protected routes 401 without a session, registration creates the account and sets a working cookie, a second registration is refused, logout clears the session, wrong-password fails, correct-password re-authenticates, and 5 failed attempts triggers the 429 lockout. Separately, ran the real app in-browser: first-run setup screen → register → auto-login → full Dashboard/Workspace load correctly with real data → logout → correct "Log In" (not "Create Account") mode shown → wrong password shows a clear inline error → correct password restores the session.

## Multi-Provider Text-to-Speech (TTS)

**Provider adapter pattern, not a class hierarchy.** A `TtsProviderAdapter` (`server/services/ttsProviders.ts`) is just three functions — `testConnection`, `fetchVoices`, `generateSpeech` — with no shared base class. Adding a provider is: write the three functions, add one entry to the `adapters` map, add one entry to `TTS_PROVIDERS` in `src/types/ttsSettings.ts`. Nothing else in the system (routes, settings UI, `useTtsPlayback`, `TtsPlayButton`) references Speechify by name; they all key off the `provider` string. See the architecture comment at the top of `ttsProviders.ts` for the full checklist.

**Per-provider config and voice catalogs are JSON blobs keyed by provider id (`ttsSettings.providers`, `ttsSettings.availableVoices`), not one column per provider.** This deliberately diverges from `aiSettings`' pattern of a dedicated column per provider (`openaiKey`, `openrouterKey`, ...) — that's fine for a fixed set of three long-standing providers, but would mean a schema migration every time a new TTS provider is added. The blob approach keeps additions to pure code changes, at the cost of losing column-level type safety (mitigated by the shared `TtsProviderConfig`/`TtsVoice` types).

**Voice preference resolution is two-level: per-story override, falling back to a global default.** `storyTtsPreferences` is a separate table (one row per story, unique on `storyId`) rather than a field on `stories`, so it can be absent entirely (no row = "use the global default") without a nullable-everything column on the main entity. `TtsPlayButton` and `StoryVoiceCard` both resolve `storyVoice?.voiceId ?? providers[activeProvider]?.defaultVoiceId` — the same two-level fallback in both places, not a server-side "effective voice" endpoint, since the client already has both pieces of data loaded from existing queries.

**`POST /api/tts/generate` returns raw binary audio on success, JSON on failure** — the two response shapes are told apart by HTTP status, not a `{success, ...}` envelope (unlike `test-connection`/`voices/refresh`, which always return 200 with a success flag so the settings UI can toast either way from one code path). Generation is different: a future non-UI consumer of this endpoint should get a normal REST contract (audio bytes or a proper error status), and the client needs a dedicated `fetchBlob` helper (`src/services/api/apiFactory.ts`) alongside `fetchJSON` regardless, since a Blob response can't be parsed as JSON.

**`useTtsPlayback` is the one playback primitive; UI components never talk to `<audio>` directly.** It owns blob-URL lifecycle (create on `speak()`, revoke on `stop()`/`pause→never used again`/unmount) and exposes `speak`/`pause`/`resume`/`stop` plus `isGenerating`/`isPlaying`/`isPaused`. `TtsPlayButton` (chat messages) and the Preview buttons in `TtsSettingsCard`/`StoryVoiceCard` are both thin wrappers around it — three UI surfaces, one state machine, so a future "read this whole chapter" feature has zero new plumbing to write.

**`TtsPlayButton` renders `null` outright when TTS is disabled**, rather than rendering a disabled button — the enable/disable toggle is meant to fully hide the feature for users who don't use it, not leave inert controls scattered through every chat message.

**Bug found and fixed via live testing with a real Speechify API key:** `GET /v1/voices` does not return a bare array — the real REST response is `{ voices: [...], next_cursor, has_more }`. The official `@speechify/api` npm SDK's TypeScript types show `list(): Promise<GetVoice[]>`, because the SDK unwraps that envelope internally before returning to its own consumers; since this project talks to the raw REST endpoint directly (no SDK dependency), the code had been built against the SDK's post-unwrap shape and failed with `voices.map is not a function` the first time a real key exercised it. Fixed by reading `body.voices`. `has_more` was `false` even for the full 949-voice catalog, so pagination isn't implemented — noted in a comment as something to revisit if a real account ever needs it.

**Verified end-to-end with a real Speechify API key** (provided directly by the user for testing, used transiently and never persisted to memory or committed anywhere): `test-connection` succeeded, `voices/refresh` returned all 949 real voices with correct fields after the fix above, and `generate` returned genuine playable audio (`Content-Type: audio/mpeg`, valid MP3 `ID3` header bytes) using the server's fallback-to-default-voice path. Separately verified the full client-side play/pause/resume state machine by faking only the network layer (a real WAV blob returned from a patched `fetch`, all other code — hook, blob handling, `<audio>` element — genuine): Read aloud → Pause → Resume → Pause, and natural playback-end correctly resets to idle. The database row and all test artifacts (including the API key) were cleared after verification.

## Humanizer (AI Rewrite Pass for Selected Text)

**Scope was narrowed deliberately before building anything.** "Humanize" is ambiguous along three axes that materially change the architecture — where it applies (editor vs. chat), how it triggers (on-demand vs. automatic post-process), and what "intensity" means (presets vs. a continuous value). Asked the user up front rather than guessing: landed on Main Editor only, an on-demand button (not a silent automatic pass — avoids doubling API cost/latency on every generation and avoids surprising users by silently rewriting their output), and preset intensity levels (Light/Medium/Strong) over a slider.

**Reuses the existing per-feature AI endpoint system instead of building its own.** Added `"humanizer"` to `FeatureKey` (`src/types/aiSettings.ts`) so `buildClientForFeature("humanizer")` just works — a dedicated (e.g. smaller/faster/local) model can be configured for it in Settings → Feature Endpoints with zero new code, since that UI already renders generically off `FEATURE_KEYS`/`FEATURE_LABELS`.

**Intensity is three fixed system prompts, not a user-editable Prompt.** Unlike the general Prompts feature (system/user/assistant messages the user can edit freely), Humanizer's "how much it should do" dial is a small, closed set of canned instructions + a matching temperature (`server/services/humanizerService.ts`) — the point of a dedicated settings surface was a simple dial, not exposing the full prompt editor for something meant to be a quick action.

**`humanizerSettings` is a single global row with no per-project override** — deliberately simpler than TTS's global+per-story voice resolution, since nothing in the request asked for per-project behaviour and there's no natural per-story "intensity" concept the way there's a per-story narrator voice.

**The rewrite endpoint always returns 200 with `{success, text?, message?}`**, matching the TTS `test-connection`/`voices-refresh` soft-fail convention (not the binary-response `/tts/generate` pattern) — the response here is always JSON, so there's no need for HTTP status to carry meaning; the client just checks `.success` and toasts either way.

**Wired into the existing selection-based rewrite toolbar (`FloatingTextFormatToolbarPlugin`) as a new button, not a new toolbar.** That component already replaces the Lexical selection with AI output for the `selection_specific` Prompt flow — Humanize reuses the same `getSelectedText()`/`editor.update()` replace pattern, but deliberately does *not* apply the existing convention of formatting AI-inserted text as italic: that convention flags *newly generated* content as AI-authored, whereas Humanize rewrites the user's *own* selected text specifically to read as less AI-like, so marking the result as visually "still AI" would be backwards.

**The button is hidden entirely when Humanizer is disabled** (checked via `useHumanizerSettingsQuery` in the toolbar), not shown-but-disabled — same principle as `TtsPlayButton` in the TTS work: a toggle should remove the feature from view for people who don't use it.

**`src/services/api/client.ts` was split up while making this change.** It had already grown past the project's 250-line lint limit during the earlier TTS work (uncommitted at the time), and adding `humanizerApi` pushed it further over. Rather than ignore the warning, moved `ttsApi` and `humanizerApi` into their own files (`ttsClient.ts`, `humanizerClient.ts`), re-exported from `client.ts` so none of the ~30 existing call sites needed to change their import path.

**Verified end-to-end in the real app**: the settings card renders and persists (enable toggle + intensity, confirmed via reload), "Humanizer" appears automatically in the Feature Endpoints list, the toolbar button is completely absent when disabled and appears immediately when enabled, and clicking it with no AI provider configured in the environment produces the exact real error path end-to-end (route → `generateHumanizedText` → `buildClientForFeature` returns `null` → the guidance message is toasted and the button cleanly resets to idle) — not a mocked failure.

## Concrete Beats (Inline Scene-Beat Tagging, Task 1)

**Naming collision with the existing "Scene Beat" feature was deliberately avoided, not glossed over.** The app already has `sceneBeats` (`src/types/story.ts` `SceneBeat`) — a command a writer inserts for the AI to expand into prose, represented by a `DecoratorNode` that gets *replaced* on acceptance. The new feature tags spans of prose that already exist, for tracking/consistency, and has nothing to do with AI generation. Both are called "beat" by their own naming, so the new table/type/route/component names are all prefixed distinctly (`concreteBeats`, `ConcreteBeat`, `/api/beats`, `BeatMarkNode`) and the distinction is called out in a comment everywhere the two could plausibly be confused.

**Built on `@lexical/mark`'s `MarkNode`, which was already registered in this codebase but completely unused.** This is the same node the official Lexical "Comments" example uses to anchor a comment thread to a span of text — it already solves the hard parts (surviving edits in and around the marked span, overlapping marks, JSON round-tripping) that a hand-rolled inline node would have to reimplement. `BeatMarkNode` subclasses it purely to also carry `beatType` on the node itself (`src/components/story-editor/nodes/BeatMarkNode.ts`), so the type travels with the document and needs no separate lookup on load. The subclass registers its own Lexical node type (`beat-mark`), so it coexists with any future feature (e.g. real comments) that uses bare `MarkNode`.

**The database row's `id` *is* the Lexical mark's id — no separate anchor-id column.** `$wrapSelectionInMarkNode` takes an arbitrary id string; since `createCrudRouter` already generates a UUID server-side on insert, the beat is created first (getting its id from the server), then that same id is passed to wrap the selection. One id, one source of truth, no risk of the two drifting apart.

**Inline mark colour uses hand-written CSS classes (`beat-mark--<type>` in `PlaygroundEditorTheme.css`), not Tailwind utility classes, despite Tailwind being the norm everywhere else.** The existing `.PlaygroundEditorTheme__mark` base style (a fixed yellow) is itself plain CSS with single-class specificity from Lexical's `theme.mark` config. Relying on Tailwind utilities to out-specificity that would depend on stylesheet injection order, which is fragile and unverifiable without inspecting the built CSS. A combined selector (`.PlaygroundEditorTheme__mark.beat-mark--wardrobe_item_change`) reliably wins on specificity regardless of order. Regular React UI (badges in the beats panel) still uses Tailwind normally — this is specifically about content rendered inside the Lexical editor's DOM.

**`source`/`status` columns exist now even though Task 1 only ever writes `'manual'`/`'confirmed'`.** The overall feature (per its own spec) requires AI-suggested beats with an approval/rejection flow later — mirroring `codexPendingChanges`' `'pending'|'approved'|'rejected'` convention now (as `'confirmed'|'pending'|'rejected'`, since manual beats need no approval step) means that later task is an application-logic change, not a schema migration. Same reasoning as `ttsSettings.providers` being a JSON blob in the TTS work — pay for extensibility where a concrete future requirement already names it, not speculatively everywhere.

**Deleting a beat from the management panel needed a way to reach into the Lexical editor from outside its component tree, and there was no existing precedent for that in this codebase.** The Concrete Beats panel is a sidebar drawer (`StoryEditor.tsx`) rendered as a sibling of the `LexicalComposer`, not a descendant — the existing Notes/POV/Outline panels never needed editor access (Notes is its own separate editor instance; POV/Outline are plain form fields), so this is a new problem. Solved with a small DOM `CustomEvent` bridge (`src/features/beats/beatEvents.ts`): the delete mutation dispatches `concrete-beat-deleted` with the beat's id, and `BeatMarkSyncPlugin` (registered inside the composer, alongside the other editor plugins) listens and unwraps the matching `BeatMarkNode` via `$nodesOfType(BeatMarkNode)` + `hasID()` + `$unwrapMarkNode`. Simpler and less invasive than lifting the editor instance up through `StoryEditor.tsx` or restructuring the drawer to live inside the composer tree.

**Known gap, not fixed in Task 1**: the reverse direction — deleting the marked *text itself* through normal editing — isn't synced back to the database. Lexical's `MarkNode.canBeEmpty()` is `false`, so the mark node itself is pruned automatically once its content is gone, but the `concreteBeats` row is left behind with a stale snippet. Closing this needs a `registerMutationListener(BeatMarkNode, ...)` watching for node removal, which is a reasonable follow-up but wasn't in Task 1's scope (manual marking + storage + UI).

**Verified end-to-end in the real app**: created a beat via the floating toolbar (all 7 types render in the picker), confirmed the correct colour-coded `<mark>` renders with the right classes and computed CSS (no yellow bleed-through from the base style), confirmed the database row persists with the exact selected text, reloaded the page and confirmed the mark survives the full Lexical JSON serialize/deserialize round-trip, opened the Beats panel and confirmed the entry displays correctly, deleted it and confirmed both the database row *and* the visual mark disappear together (this exposed and let me fix the cross-tree sync gap above), and confirmed the removal itself persists after a further reload.

## Concrete Beats — Character Codex Integration (Task 2)

**`concreteBeats.characterId` is a real foreign key, unlike `chapters.povCharacter`/`sceneBeats.povCharacter` which store a plain display-name string.** Those two only ever need a label for prompt-templating (`{{pov}}`). A beat needs to reliably re-fetch a character's *structured* `codexState` (wardrobe/appearance/wounds/items) to show it in the marking UI and, later, to feed the RAG Scanner — a name string can't do that (renames would silently break the link, and there's no way to actually query "this character's current wardrobe" from a name alone).

**Discovered while building this: FK enforcement (`PRAGMA foreign_keys`) is off database-wide in this app** — `server/db/client.ts` only sets `journal_mode = WAL`, nothing enables foreign key constraint checking. This means *every* `onDelete: "cascade"`/`"set null"` clause across the entire schema (not just this new column) is decorative unless enforced by application code elsewhere; SQLite silently allows orphaned rows. This is a pre-existing, app-wide characteristic, not something introduced or fixed here — flagged for awareness, not addressed, since retroactively enabling it on a populated database is a separate, riskier piece of work than "Task 2: Codex integration for beats." Practical consequence: `characterId` can point to a deleted lorebook entry, so the UI (`ConcreteBeatsPanel`) explicitly handles a non-resolving id as "Character removed" rather than assuming it always resolves.

**Codex data is pulled live via the existing lorebook query/context, not duplicated onto the beat.** `characterId` is the only thing stored — `CodexStatePreview` (shown in the beat-marking popover) and the character-name badge (in the beats panel) both resolve it against `useLorebookContext()`'s already-loaded entries. No new server endpoint was needed: the full `LorebookEntry` (including `codexState`) was already being fetched for the story via the existing hierarchical lorebook query that the rest of the editor uses (Tags matching, POV character selection, etc.).

**The beat-marking UI changed from a plain dropdown (Task 1's `BeatTypeMenu`) to a `Popover` form (`BeatMarkPopover`)**, since picking a beat type *and* an optional character *and* reviewing a Codex preview before confirming doesn't fit a menu-item-per-click interaction — `BeatTypeMenu.tsx` was deleted rather than left as dead code alongside its replacement.

**Character selection is optional and available for every beat type**, not gated to "wardrobe/item change" or "character movement" specifically. Dialogue tags need a speaker, physical actions need an actor, sensory details are often a specific character's perception — restricting the picker by type would be guessing intent the task didn't ask for; leaving it open and optional covers all of them without extra logic.

**Verified end-to-end with real (seeded) Codex data**: enabled Codex tracking on a demo character with wardrobe/appearance/wounds/items populated, opened the Mark Beat popover, confirmed all 5 story characters listed, selected one and confirmed the exact seeded state rendered correctly under "Current state — Elena Cross" grouped by section, applied the beat and confirmed `characterId` persisted correctly in the database, confirmed the linked character's name renders as a second badge in the Beats panel alongside the beat-type badge, and confirmed removing the beat still correctly unwraps the mark (Task 1's cross-tree sync fix) even with a character attached. Test data (the beat and the demo character's Codex fields) was cleared after verification.

## Concrete Beats — AI Suggestions & Background Auto-Tagging (Task 3)

**Deliberately deviates from `entityDetector`/`codex.ts`'s ephemeral `/detect` precedent.** The existing convention (`POST /api/codex/detect`) returns candidates that only get persisted if the user explicitly creates them — nothing is written until approval. Beats' `POST /api/beats/detect` (`server/services/beatDetector.ts`) instead persists every valid suggestion immediately as a `concreteBeats` row with `status: "pending"`. Reason: background auto-tagging runs unattended (on a save debounce, with nobody necessarily watching), so suggestions must survive a page reload or the user closing the tab between detection and review. An ephemeral, in-memory-only result would be lost the moment the response wasn't immediately acted on. `status: "pending"` already existed as a schema value from Task 1 for exactly this eventuality (see Task 1's note on `source`/`status` being added ahead of need) — no migration was needed for Task 3.

**Suggestions get no inline editor highlight while pending — only the review panel shows them, styled distinctly (dashed amber border + "AI Suggested" badge, `SuggestedBeatCard.tsx`).** Wrapping unconfirmed AI text in a live `BeatMarkNode` immediately would mean mutating the user's document based on an unreviewed suggestion while they might be actively typing elsewhere in it — a real risk of visual clutter or edit conflicts for something that might get rejected seconds later. The inline mark is only created on **Accept** (`BeatMarkSyncPlugin`'s new `BEAT_ACCEPTED_EVENT` handler), via the same cross-tree DOM-event bridge Task 1 built for delete-sync (`beatEvents.ts`) — accepting has no live text selection to anchor to (the user may not even be looking at the editor when they click Accept from the panel), so a new helper (`$findTextNodeRange` in `beatTextSearch.ts`) does a plain substring search over the document's TextNodes to locate the snippet and wrap it fresh. This deliberately doesn't search across node/paragraph boundaries (AI snippets are expected to be short, single-run phrases); if the exact text can't be found — e.g. the chapter was edited since detection — the beat still confirms in the database, just without a highlight, and the user gets a toast explaining why.

**Two independent debounce timers off the same `editor.registerUpdateListener`, not one.** `SaveChapterContentPlugin` already had a 1000ms debounce for content saving; background beat detection adds a second, much longer 8000ms debounce on the same listener, deliberately kept as its own `lodash.debounce` ref rather than chained onto the save mutation's `onSuccess`. A detection failure (e.g. no AI provider configured) must never affect the actual content-save path, and detection firing on every keystroke-triggered save (like the 1s save timer does) would be excessive for something that hits an LLM. The two timers are cancelled independently on unmount.

**Auto-detect is opt-in, off by default, gated by a plain localStorage toggle (`useAutoDetectBeats.ts`), not a server-side setting.** Mirrors the existing `useShowModelThinking` pattern (`useSyncExternalStore` + a module-level cache + a `storage` event listener for cross-tab sync) rather than adding a new column to any settings table — this is a lightweight, purely-client-side UX preference with no server-side consequence, so it doesn't need to round-trip through the API or be considered "AI settings."

**The base `useDetectBeatsMutation` hook has no built-in toast/error handling** — deliberately, unlike every other beats mutation hook. The manual "Suggest Beats" button (user is watching, wants full feedback) and the silent background auto-trigger (runs unattended, shouldn't interrupt with toasts on every failure) need different feedback for the exact same underlying mutation, so each call site supplies its own `onSuccess`/`onError` via the mutation's per-call options rather than the hook baking in one behavior.

**`POST /api/beats/chapter/:chapterId/reject-all` is a dedicated route on the beats CRUD router's `customRoutes` hook, not N individual `PATCH` calls from the client.** A bulk status flip is one `UPDATE ... WHERE status = 'pending'` server-side; doing it as a loop of per-row client mutations would be slower, non-atomic, and would fire N separate query invalidations for one user action.

**Verified end-to-end in the real app**, including the manual-trigger, edit, and bulk-reject paths that don't require a live LLM: confirmed `POST /api/beats/detect` correctly returns the soft-fail shape (`{success: false, message}`) and toasts it when no AI provider is configured (this environment's actual state) rather than erroring the whole request; seeded synthetic `pending`/`ai_suggested` rows directly via the API to exercise the review UI without a live model; confirmed the pending section renders with the dashed/amber "AI Suggested" styling and both suggestions listed with correct per-type badges; Accept correctly flips status to `confirmed`, moves the card to the Confirmed list with a small sparkles indicator, and inserts a real inline `<mark>` in the live Lexical document containing the accepted text; Edit correctly opens inline beat-type/character selects, and Save Changes persists the edited `beatType` to the database while leaving `status` at `pending` (an edit doesn't imply acceptance); Reject All correctly flips all remaining pending beats to `status: "rejected"` (confirmed via direct API check — rejected, not deleted) and clears the pending section in one action; the "Auto-detect on save" switch persists to `localStorage` correctly. All test beats and a stray inline mark left over from manual test setup were cleaned up afterward so the shared demo story content wasn't polluted.

## Concrete Beats — Polish & Guide (Task 4)

**The inline mark's `.selected` CSS state was silently broken before this task, not just under-styled.** `.PlaygroundEditorTheme__mark.selected` (the base rule) and `.PlaygroundEditorTheme__mark.beat-mark--<type>` (added in Task 1) are both two-class selectors — equal specificity — and the beat-type rules are declared later in the stylesheet, so they always won the tie once a beat mark also carried Lexical's `.selected` class, meaning clicking into a colored beat mark showed no different visual feedback at all versus not-selected. Fixed by adding a `.beat-mark--<type>.selected` variant per type (deepened opacity, same hue) rather than trying to reorder the base rules — an explicit three-class selector for the combined state is clearer than relying on declaration order to keep working correctly in the future.

**Inline marks now carry a `title` attribute (the beat type's label) set in `BeatMarkNode.createDOM`/`updateDOM`.** Colour alone isn't a reliable way to distinguish 7 categories, especially for colour-blind users — a native browser tooltip on hover is a one-line addition that doesn't require any new UI chrome, and it reads the same `CONCRETE_BEAT_TYPE_MAP` already used everywhere else, so it can't drift out of sync with the badge labels.

**Added a colour-key popover (`BeatTypeLegend.tsx`) instead of an always-visible legend strip in the panel.** An always-on legend competes for space in an already content-dense drawer (Suggest Beats button, auto-detect toggle, suggested/confirmed sections) for something only needed occasionally (learning or double-checking the mapping) — a small ⓘ trigger next to the existing controls keeps the common case uncluttered while still making the full type→colour→description mapping one click away.

**The Guide entry (`concrete-beats.mdx`) explicitly restates the Scene Beat vs. Concrete Beat distinction as its first callout**, not just in a code comment — this is the single most likely point of user confusion given the shared word "beat," and the in-app help is where a confused user actually is when the question comes up, not in the codebase.

**Verified in the real app**: hovering a manually-marked beat mark shows the correct type-label tooltip; forcing the `.selected` class confirms the type-specific deepened colour applies instead of falling back to the generic yellow selected style; the ⓘ colour-key popover opens from the Beats panel and lists all 7 types with matching badge colours and descriptions; the new "Concrete Beats" tab renders correctly in the Guide page alongside the existing six tabs, with working callouts, tables, and lists via the same MDX pipeline. `tsc --noEmit` (frontend + server) and a full-project `oxlint` sweep are both clean — the pre-existing 21 warnings elsewhere in the codebase are unchanged and unrelated to this feature.

## Editor MultiView — Split-Screen Foundation (Task 1)

**Scoping check before writing any code.** "Floating panels that can be docked or floated" (a later task in this feature) is ambiguous between a lightweight docked/floating toggle and a full VS Code-style drag-to-any-edge docking framework — the latter would need a new heavy dependency and a much larger engineering/maintenance surface. Asked the user up front rather than guessing (per CLAUDE.md's "ask before major architectural changes"); got the lightweight toggle, built entirely on existing Radix/shadcn primitives with no new dependency for that part.

**The pane tree is a plain recursive union type (`EditorLayoutNode` = `{type: "pane"}` | `{type: "split", direction, sizes, children}`), not a flat list with parent pointers.** Splitting, closing, and resizing are all pure tree transforms (`layoutTree.ts`) operating on immutable snapshots — `splitPaneInTree` replaces a pane in place with a 2-child split (original pane + a fresh duplicate defaulting to the same chapter), `closePaneInTree` removes a pane and collapses any split left with only one child back into that child (so the tree never carries a redundant single-child split node). `EditorPaneState` deliberately stores a single `chapterId` rather than a tab list already — a later task adds tabs, and extending a list-of-one to a real list is a much smaller migration than un-baking a wrong assumption now.

**Splitting an existing single-editor page-scroll layout into resizable panes exposed a real, pre-existing height-containment bug — not something introduced by this feature, but something this feature was the first to actually need fixed.** `MainContent.tsx` wraps every tool in a `min-h-full` div so content-heavy tools (Notes, Lorebook lists) can grow taller than the viewport and let `main`'s `overflow-auto` page-scroll — which happened to also apply to the editor, even though the editor's own CSS (`.editor-scroller { overflow-y: auto }`, already present, apparently unused in practice) was clearly built for *internal* scrolling. Because `min-h-full` only sets a minimum, the whole ancestor chain quietly grew to match the tallest content on the page instead of the viewport, which single-editor and side-by-side (horizontal) panes never surfaced — only a *vertical* split did, since dividing height between stacked panes requires an ancestor with a real, bounded height, and dividing width doesn't. Fixed by giving `MainContent.tsx` a per-tool branch: the editor tool gets `h-full overflow-hidden` (a real boundary), every other tool keeps `min-h-full` unchanged. This also means the single-editor case now scrolls its own text internally with a fixed toolbar/sidebar, instead of the whole page (including the icon rail) scrolling together — arguably a fix, not just a workaround, and a necessary precondition for split panes to size correctly at all.

**Per-pane chapter isolation required a new context layer, not prop drilling.** `EmbeddedPlayground`, `SaveChapterContentPlugin`, `LoadChapterContentPlugin`, `FloatingTextFormatToolbarPlugin`, `SceneBeatComponent`, and `SceneBeatMatchedEntries` all previously read `currentChapterId`/`currentStoryId` straight from the app-wide `StoryContext`. A new `EditorPaneContext` (`useEditorChapterId`/`useEditorStoryId`) sits between them: inside a MultiView pane it returns that pane's own chapter/story; outside MultiView (or in any future call site nobody's migrated yet) it transparently falls back to the same global `StoryContext` values as before. This is why the single-pane path is provably unchanged — the fallback *is* the old behavior, not an approximation of it.

**`useChapterMatching` (lorebook tag-matching, used by `SceneBeatComponent` and the shell's Tags drawer) had to change from "one flat Map" to "one Map keyed by chapterId," not from one provider instance to several.** The first version tried nesting a fresh `ChapterMatchingProvider` per pane, which broke the shell-level Tags drawer entirely (it lives outside any pane, so it was reading a provider nothing wrote into anymore). Keying a single shared provider by chapter, instead, means each pane's `LorebookTagPlugin` only ever touches its own chapter's slice (no cross-pane leakage) while the shell's Tags drawer still reads whichever chapter is currently focused — the same single-provider architecture as before, just chapter-scoped internally.

**Pane focus flows one way into the global `currentChapterId`, not both ways.** Clicking into a pane (or changing its chapter picker) calls the global `setCurrentChapterId`, so the TopBar's `ChapterSwitcher`, the download button, and the Tags/Outline/POV/Notes/Beats drawers all correctly track "whichever pane you're using" without those five drawer components needing any MultiView-awareness at all. The reverse direction (picking a chapter from the TopBar while a multi-pane layout already exists reaching back into a specific pane) was deliberately left unwired — round-tripping both directions risks a feedback loop between "last-focused pane" and "last global pick," and the per-pane chapter picker is the supported way to change what an existing pane shows. A real (if narrow) known gap, not a bug: picking a different chapter from the TopBar while 2+ panes are open won't visibly change any pane.

**Bug found during manual testing, not caught by typecheck/lint: a stale-closure bug in the pane's chapter-picker `onValueChange` handler.** The first version called a shared `focusPane()` helper after `setPaneChapter(...)`, but `focusPane` read `pane.chapterId` from the render-time prop — which is still the *old* value until the state update it just triggered actually re-renders the component. Fixed by having the picker's handler push the newly-picked `chapterId` directly into `setCurrentChapterId`, rather than re-reading it off `pane` a moment later. Also found: `EditorTool.tsx`'s pre-existing "loading chapter…" / "chapter not found" guards (which unmount `StoryEditor` entirely while `currentChapterId`'s own query is in flight) actively destroyed the whole pane tree every time a pane's chapter selection changed to something not yet cached, because that selection updates the same global `currentChapterId` those guards watch. Removed both guards — `StoryEditor`/`EditorMultiView`/`EmbeddedPlayground` already handle "no chapter loaded yet" per pane without needing the whole shell to unmount.

**Verified end-to-end in the real app**: single-pane view is visually and functionally identical to before (confirmed via `main`'s scrollHeight now matching its bounded height rather than growing to content, with `.editor-scroller` handling internal scroll instead); horizontal split renders two independently-editable, correctly-loaded panes; vertical split (after the height-containment fix) renders correctly-proportioned, independently resizable stacked panes; a nested split (a horizontal split whose first child is itself vertically split) renders and resizes correctly; picking a different chapter in one pane's header leaves every other pane untouched and correctly updates the TopBar/global selection to match; typing in one pane never appears in another; marking a Concrete Beat from a specific pane's floating toolbar correctly records against *that pane's* chapter (verified via direct API check), not the pane that happened to be active before the split. All test beats, inline marks, and one instance of stray typed text that leaked into a demo chapter during testing were cleaned up afterward. `tsc --noEmit` (frontend + server) and a full-project `oxlint` sweep are both clean — the same 21 pre-existing warnings elsewhere, zero new ones.

## Editor MultiView — Tabs & Floating Panels (Task 2)

**Mid-course correction from the user**: the plan going in was "tabs = multiple chapters open per pane." The user clarified the actual goal was to let the Lorebook and the existing StoryEditor side-drawers (Tags, Outline, POV, Notes, Beats) become tabs too — i.e. tabs aren't chapter-only, and "floating panels that can be docked or floated" (Task 1's deferred second requirement) and "tabbed editor support" turn out to be the *same* underlying mechanism wearing two hats, not two separate features. Redesigned around that before writing code rather than bolting tool-tabs on afterward.

**`EditorPaneState.tabs` moved from `chapterId: string` to `tabs: PaneTab[]`, where `PaneTab.content` is a tagged union (`PaneTabContent`) — `{kind: "chapter", chapterId}` plus one variant per tool panel (`lorebook`, `tags`, `outline`, `pov`, `notes`, `beats`).** The four chapter-scoped tool kinds carry their own explicit `chapterId` rather than implicitly following "whichever chapter tab is active in this same pane" — a tab's content is fully self-contained, so an "Outline" tab keeps showing the right chapter's outline even if you later switch that same pane's chapter tab to something else.

**"Docked" and "floating" are the same `PaneTabContent` value living in two different places, not two implementations of each panel.** A docked tab lives in a pane's `tabs` array (tiled into the resizable grid, from Task 1). A floating panel lives in a separate `FloatingPanelsContext` list (`{id, content, x, y, width, height}` — plain pixel state, not part of the pane tree, since it doesn't participate in splits/resizing between siblings). Both render through the same `PaneTabContentView` switch (chapter → `EmbeddedPlayground`, lorebook → `LorebookPage`, tags → `MatchedTagEntries`, outline/pov/notes/beats → the existing chapter-scoped components), so "what does an Outline tab look like" is decided exactly once regardless of where it's displayed. "Float" on a tab is `closeTab` + `addPanel` with the same content; "Dock" on a floating panel is the reverse (`closePanel` + `addTab` into the currently active pane).

**Floating panels are hand-rolled (pointer events + refs), not a new dependency.** One draggable title bar (`onPointerDown`/`onPointerMove`/`onPointerUp` with `setPointerCapture`, tracking a start-position ref) and one resize handle (the same pattern, tracking start-size instead) is the entire mechanism — deliberately not reaching for a drag/resize library for something this small, consistent with the project's general "avoid heavy dependencies" bias (see the TTS/Humanizer/RAG decisions above). Z-order is just array order in `FloatingPanelsContext` — "bring to front" moves the clicked panel to the end of the array, which is also its DOM paint order.

**`MatchedTagEntries` gained an optional `chapterId` prop instead of duplicating the component.** The existing shell-level Tags drawer usage (`<MatchedTagEntries />`, no props) keeps reading the app-wide focused chapter unchanged; a MultiView "Tags" tab passes its own tab's `chapterId` explicitly. Same reasoning as `EditorPaneContext`'s fallback pattern from Task 1 — one component, the caller's context determines which chapter it means.

**`updatePaneInTree` is new shared plumbing in `layoutTree.ts`, and `paneTabs.ts` holds the actual tab operations (`addTabToPane`/`closeTabInPane`/`setActiveTabInPane`) as small pure functions over a single `EditorPaneState`.** Rather than writing three more full-tree recursive traversals (one each for add/close/activate, alongside the existing `splitPaneInTree`/`closePaneInTree`), `updatePaneInTree(node, paneId, updater)` finds the one matching pane and applies an arbitrary pane-level transform — the tab operations don't need to know anything about the surrounding split tree at all.

**Closing the last tab in a pane triggers `closePaneInTree` (removing the whole pane), and closing the last tab in the last pane is disallowed** — the same "there must always be something open" rule Task 1 established for panes now also applies one level down, at the tab level.

**`DropdownMenuSub`/`DropdownMenuSubTrigger`/`DropdownMenuSubContent` were defined but never exported from `src/components/ui/dropdown-menu.tsx`** (dead code sitting there since whenever that file was generated) — needed for the "+" add-tab menu's "Chapter ▸" submenu of individual chapters. Exported them (plus `DropdownMenuSub` itself, which didn't exist at all) rather than reimplementing submenu behaviour by hand.

**Verified end-to-end in the real app**: opened Lorebook as a tab and confirmed its full category browser renders and works inside a pane; opened Outline/Beats tool tabs scoped to a specific chapter and confirmed correct labels ("Outline — Prague Protocol") and working content (Concrete Beats' Suggest Beats button, the outline textarea); closed a tab and confirmed only that tab disappears; floated a tab out (Beats) and confirmed it renders as a movable window with the same working content; dragged it (title bar pointer-event sequence, confirmed via the panel's `style` attribute changing) and resized it (corner handle, confirmed width/height both changed); docked it back and confirmed it reappears as a pane tab and the floating window disappears; split a pane with 2 tabs open and confirmed the new pane gets only a copy of the tab that was active, while the original pane keeps both. No new beats/content were created during this pass, so no cleanup was needed. `tsc --noEmit` and a full-project `oxlint` sweep are both clean — same 21 pre-existing warnings, zero new ones (one new a11y warning on the custom tab element was fixed by adding `role="tab"`/keyboard handling rather than suppressed).

## Editor MultiView — Persistence & Keyboard Shortcuts (Task 3)

**localStorage, not a server table, and per-story keys** (`editor-multiview-layout-{storyId}`, `editor-multiview-floating-{storyId}`) — this is the same call already made for every other piece of per-story *workspace UI* state in this app (current chapter, current tool, right-sidebar collapse, in `StoryContext`/`WorkspaceContext`), none of which live server-side. A layout is "how I like to look at this story," not story content — it doesn't need to survive a localStorage clear or sync across the Tailscale-connected machines CLAUDE.md cares about the way chapter text does.

**A hand-rolled structural validator (`layoutValidation.ts`), not zod, for the recursive tree shape.** zod is already a dependency and used elsewhere for API payloads, but a full schema for a recursive tagged-union tree (`EditorLayoutNode`) would be more ceremony than the equivalent handful of small `isRecord`/`isValidX` guard functions, given this only needs to run once per mount rather than validate a wide, evolving external API surface. Deliberately validates *shape* only (right fields, right types, `activePaneId` actually points at a pane that exists in the tree) — not whether a `chapterId` still resolves to a real chapter, since that's a data-freshness question already handled at render time, not a corruption question.

**A layout can now outlive the chapter it points at — restored from a previous session after that chapter was deleted — so `PaneTabContentView`'s `ChapterScopedContent` needed to stop conflating "still loading" with "doesn't exist."** Before persistence, an invalid `chapterId` in a tab was a near-impossible edge case (the in-memory tree never survived long enough to reference something stale). After persistence, it's a realistic scenario the first time. Fixed by checking `isLoading` explicitly and showing "This chapter no longer exists" once the query has genuinely resolved to nothing, instead of spinning forever.

**Both persistence effects are debounced (400ms), not saved on every state change.** `setSplitSizes` fires on every pixel of a resize-handle drag, and a floating panel's `updatePanel` fires on every `pointermove` while dragging/resizing — writing to localStorage on each of those would be wasteful. Split/tab/pane operations are infrequent enough that the debounce is imperceptible.

**Discovered while testing, not something a strict TS type could catch: `react-hotkeys-hook` ignores keydowns from contenteditable/form elements unless `enableOnContentEditable`/`enableOnFormTags` are explicitly set.** Since the Lexical editor *is* a contenteditable, and it's focused the entire time someone is actually writing, every shortcut in this feature would have been silently inert during the one activity MultiView shortcuts are for. Fixed by setting both options on every `useHotkeys` call in `useEditorMultiViewShortcuts.ts`.

**Also discovered while testing: bracket-key shortcuts (`mod+]`/`mod+[`) don't reliably match in this version of the library, including the app's own pre-existing chapter-navigation shortcuts — not just something new here.** `react-hotkeys-hook` matches non-modifier keys by normalizing `KeyboardEvent.code` (e.g. `"BracketRight"` → `"bracketright"`), but a literal `"]"` typed into a hotkey string normalizes to `"]"` — these never match. Rather than risk shipping shortcuts on the same shaky foundation, this feature's tab-cycling shortcuts use vi-style `mod+alt+j`/`mod+alt+k` instead of brackets — letters and arrow keys normalize consistently (confirmed: `"KeyJ"` → `"j"`, `"ArrowRight"` → `"arrowright"`, matching their string-form equivalents exactly). The existing `mod+]`/`mod+[` chapter-nav shortcuts were not touched — that's pre-existing, unrelated code — but this is worth knowing if they're ever reported as flaky.

**All ten shortcuts use `mod+alt+<key>`, a key space nothing else in the app touches**: `mod+alt+right`/`down` (split), `mod+alt+w` (close pane), `mod+alt+j`/`k` (cycle tabs in the active pane), and `mod+alt+l/t/o/p/n/b` (toggle Lorebook/Tags/Outline/POV/Notes/Beats as a tab in the active pane — same content-equality check as the "float" action, so "toggle" means close-if-open-else-open, not always-add). Only mounted while `EditorMultiView` itself is, so there's no separate "is the Editor tool active" guard needed — unmounting already handles it.

**Verified end-to-end in the real app**: built a 2-pane layout with a Lorebook tab, an Outline tool tab, and a floated-and-dragged Beats panel; reloaded the page and confirmed the exact tab structure and the floating panel's exact dragged pixel position both came back unchanged. Verified every shortcut individually after discovering and fixing the contenteditable-focus issue: split right/down, close pane, cycle tabs forward/backward, and all six panel-toggle shortcuts (confirmed each both opens and closes its tab on repeated presses). `tsc --noEmit` and a full-project `oxlint` sweep are both clean — same 21 pre-existing warnings, zero new ones. Test layout state was cleared from localStorage afterward so the next session starts from a clean single pane.

## Story Outlining — Visual Outline Foundation (Task 1)

**A new top-level `outlineItems` table, not an extension of `chapters.outline`.** The Main Editor already has a per-chapter free-text outline field (`chapters.outline`, the "Outline" drawer). This feature is a different concern — a story-wide structural planning layer, built before or alongside prose, not a per-chapter scratch note — so it got its own table and its own "Outline" entry in the main left sidebar (next to Chapters/Lorebook), rather than replacing or extending the existing drawer. Both now coexist untouched.

**Exactly two fixed levels (chapter, scene), not an arbitrary-depth tree.** The task asks to "nest scenes/chapters," and a real arbitrary-depth outline tree is both a much bigger UI problem (generic tree DnD) and not what most outlining actually needs. `outlineItems.type` is `"chapter" | "scene"`, with `parentId` only ever pointing from a scene to its chapter — never chapter-to-chapter or scene-to-scene nesting further down. This mirrors the project's general bias (see the TTS/Humanizer/RAG decisions above) toward the concrete, tractable version of a feature over the maximally general one.

**`parentId` is a plain column, not a self-referencing FK.** This app runs with SQLite foreign-key enforcement off database-wide (see the `concreteBeats.characterId` comment) — a self-ref would need an awkward forward-declared callback for a constraint that isn't actually enforced at runtime anyway. Deleting a chapter row cascades to its scenes in application code (`routes/outline.ts`'s custom `DELETE /:id`, which overrides the generic CRUD delete by being registered first).

**Chapters reorder via drag; scenes reorder within their own chapter via a separate, chapter-scoped drag context; moving a scene to a *different* chapter is an explicit "Move to chapter" select, not a cross-context drag.** A single unified tree-DnD system that lets you drag a scene out of one chapter and into another mid-list is a substantially harder problem (tracking drop targets across nesting levels, recomputing two different parents' sibling orders from one gesture) for a feature whose actual requirement is just "reorder and nest." Two independent `dnd-kit` `SortableContext`s (top-level chapters; each chapter's own scenes) plus one small dedicated reparent control gets the same practical outcome — restructure freely — without that complexity, and follows the exact single-context sortable pattern already established by `ChaptersTool.tsx`.

**`OutlineItem.chapterId` optionally links an outline "chapter" row to a real `chapters` row, but nothing requires it.** Outlining can happen entirely before any prose exists (chapterId stays null throughout) or as a structural map layered onto chapters that are already written — the schema doesn't force either workflow.

**Bug found during verification: the generic CRUD helper's POST only auto-populates `id`/`createdAt`, not `updatedAt`, so every create 500'd against `NOT NULL constraint failed: outlineItems.updatedAt`.** Every other table with an `updatedAt` column (`notes`, `storyTtsPreferences`, `codexPendingChanges`'s `resolvedAt`) either doesn't require it NOT NULL or is written through a dedicated (non-generic-CRUD) route — `outlineItems` is the first table to combine "required `updatedAt`" with "created via the shared `createCrudRouter`." Fixed by giving `routes/outline.ts` its own `POST /` and `PUT /:id` overrides (registered first, same precedence trick as the `DELETE /:id` override above) that always stamp `updatedAt`, rather than loosening the column's NOT NULL constraint or teaching the generic CRUD helper about it for one table.

## Story Outlining — Character Arc Tracking (Task 2)

**A single junction table (`outlineItemCharacters`) with one free-text `arcNote` field, not a separate "arc" entity.** A character's "arc overview" is just the ordered sequence of outline items they're linked to, each with a short note on their development at that point — there's no separate arc record to create or manage, which keeps the mental model to "link a character to a beat in the outline, optionally say what happens to them here."

**`storyId` is denormalized onto the junction table** (derivable from `outlineItemId`, but stored directly anyway) — the same call `concreteBeats` already makes by storing both `storyId` and `chapterId` even though the latter implies the former. It lets the arc-overview query (`GET /outline/story/:storyId/arc/:characterId`) filter directly without a join back through `outlineItems`.

**The arc's "order" is computed server-side by flattening the two-level outline into reading order** (chapters by their own order, each immediately followed by its scenes by theirs) **and then filtering down to linked items** — not stored as a separate sequence number on the link itself. A link's position in the arc is always exactly wherever its outline item sits in the story, so there's nothing to keep in sync if the outline is later reordered.

## Story Outlining — AI-Assisted Outlining (Task 3)

**Same `source`/`status` convention as Concrete Beats, applied to outline rows instead of beats**: `source: "manual" | "ai_suggested"`, `status: "confirmed" | "pending" | "rejected"`. A generated chapter and its generated scenes are inserted immediately as `pending` rows (not held in-memory until the triggering request completes) — the same rationale as `detectConcreteBeatsForChapter`: generation can be slow, and suggestions need to survive a reload while awaiting review.

**Accepting a suggested chapter does not cascade-accept its suggested scenes.** Each row's `status` is independent, so a user can keep a generated chapter's shell while rejecting or hand-editing individual scenes — matches Concrete Beats' one-suggestion-at-a-time review model rather than an all-or-nothing accept.

**The generation prompt is intentionally open-ended (no fixed taxonomy to validate against), unlike `beatDetector`'s strict "concrete only" system prompt.** An outline chapter/scene is free-form narrative planning — there's no equivalent of Concrete Beats' seven-type allowlist to enforce; the only structural validation is that returned JSON parses and each item has a non-empty title.

**Context sent to the model includes both already-written chapters (from `chapters`) and already-planned outline chapters (from `outlineItems` itself), separately labeled**, so a second "Generate with AI" pass doesn't propose something that duplicates either what's already prose or what's already planned but unwritten.

## Deep Writing Sessions — Focus Mode Foundation (Task 1)

**A new "Start a Writing Session" flow, distinct from the pre-existing toolbar "Maximize Editor" button, not a replacement for it.** The toolbar already had a `Maximize`/`Minimize` icon button (tooltip was literally "Focus mode") that collapses the workspace's left and right side panels via `WorkspaceContext.isMaximised`. That's a much shallower layout toggle than what this feature asks for ("hide sidebars, minimal UI, full-screen editor" plus timers/goals/theming/wellbeing) — so rather than overload one button with two different meanings, the existing button's tooltip was renamed to "Maximize Editor" / "Restore Sidebars" (its actual behavior, unchanged) and a new `Focus` icon button opens `StartFocusSessionDialog` right next to it. **Live word count for the goal-tracking HUD comes from a new tiny cross-component store (`chapterWordCountStore.ts`), not `ToolbarContext`.** `ToolbarContext`'s `wordCount` already exists and updates live, but it's scoped to a single Lexical composer tree (one per open MultiView pane) — unreachable from a HUD that renders outside any one pane's component tree without threading pane-id plumbing through everything in between. `WordCountPlugin` (already computing and debouncing word count every 500ms) now also reports into this `useSyncExternalStore`-based module-level `Map<chapterId, count>`, following the exact pattern `useAutoDetectBeats.ts` established for a single boolean, generalized to a per-key value. A session snapshots the *starting* count via a plain (non-hook) `getChapterWordCount` read the instant it begins, so "words written" is always relative to session start, not the chapter's total.

**A session is scoped to whichever chapter was open when it started (snapshotted, not live-tracked against "whatever the current chapter is now"), and does not persist across a page reload.** Both are deliberate scope decisions: chapter-scoping avoids needing pane-id plumbing (see above) and matches "one session, one piece of writing"; not persisting active-session state (unlike Editor MultiView's layout, which *does* persist) reflects that a session is closer to a live sprint/timer than to "how I like to look at this story" — reloading mid-session ending it is the expected, simple behavior, not a bug to fix later.

## Deep Writing Sessions — Adaptive Theming (Task 2)

**Three new themes (Warm, Low Contrast, Night) are CSS-variable overrides scoped to a wrapper class on the editor's root div, never applied to `<html>`/`<body>`, and a fourth option ("Default") is simply the absence of a class.** This means picking a focus theme can never fight the app-wide `ThemeProvider`/`ThemeToggle` (light/dark/system) — the two systems don't know about each other, by design. Each theme class redefines the *same* variable names `index.css` already defines (`--background`, `--foreground`, `--card`, `--primary`, etc.), so every existing Tailwind utility class (`bg-background`, `text-muted-foreground`, ...) and every `PlaygroundEditorTheme.css` rule (which already reads `hsl(var(--foreground))` etc.) picks up the new palette automatically — no new theme-aware components needed anywhere else in the editor.

**Smooth transitions come from plain `transition: background-color/color` on the themed subtree, not from animating the CSS custom properties themselves.** CSS custom properties don't animate directly without `@property` type registration (patchy browser support) — but `hsl(var(--background))` *resolves* to a concrete color at computed-style time, and transitioning the resulting `background-color`/`color` property works perfectly well across a class swap. The transition rule is scoped to descendants of the three theme classes only (`.focus-theme-warm *`), not the whole app, so it costs nothing outside an active session.

**The theme switcher lives in two places (Start Session dialog, in-session HUD) sharing one `FocusThemeSwitcher` component** — changing your mind about the theme mid-session doesn't require ending the session first.

## Deep Writing Sessions — Wellbeing Features (Task 3)

**All three wellbeing knobs (break reminders, session-length check-in, content check-in) default OFF and are configured per-session from the same dialog as the writing goal** — nothing about wellbeing messaging appears unless explicitly turned on, matching this app's established bias (see the Concrete Beats auto-detect toggle, off by default for the same reason: an opt-in feature respects the user's own judgment rather than assuming everyone wants to be interrupted).

## RAG Index Freshness (Lorebook Auto-Index, Reindex-on-Approve) & Agent Framework Direction

**Two real staleness gaps found while auditing the RAG pipeline for a strategy/direction discussion, both fixed.** Chapters already auto-index on save (`SaveChapterContent/index.tsx`'s 8s debounce → `ragApi.indexChapter`), but `ragIndexService.ts`'s `indexLorebookEntry` was only reachable through the manual `POST /api/rag/index/lorebook/:entryId` route — nothing called it after a lorebook entry was created or edited through the normal CRUD form, so entries silently never entered the index unless someone hit that route by hand. Fixed by calling it (fire-and-forget, via the `attemptPromise` convention already used elsewhere for non-blocking calls) from `lorebook.ts`'s custom POST and PUT handlers, mirroring the chapter pattern exactly.

**Approving a Codex proposal also left the index stale.** `codexService.ts`'s `approvePendingChange` applies the proposed fields to the live lorebook entry and snapshots the result, but never told the RAG index the entry's content had changed — a hybrid search run immediately after approval could still surface the pre-approval description. Fixed with the same fire-and-forget `indexLorebookEntry` call, placed inside the `if (hasFields(changes))` branch so a no-op approval (snapshot-only, no actual field changes) doesn't trigger a pointless reindex.

**Guardrail recorded, not acted on: no manual "run scan" UI gets built going forward.** `ragScanner.ts` is backend-complete (`scan/chapter`, `scan/story`, persisted `ragScanIssues`, progress polling) but has zero frontend — confirmed nothing in `src/` calls any `/api/rag/scan/*` or `/api/rag/issues/*` route. Building a manual trigger button now would be thrown away the moment background scanning (below) exists, so it stays deliberately unbuilt until the agent framework owns it.

**Known gap found, not fixed here (pre-existing, out of scope for this pass): deleting a lorebook entry doesn't clean up its RAG index.** Verification below deleted a test entry via the normal `DELETE /api/lorebook/:id` route (generic CRUD, no custom delete handler in `lorebook.ts`) and found its `ragChunks`/`vec_chunks`/`fts_chunks` rows were left behind — `removeEntityFromIndex` is never called from the delete path. Cleaned up manually for this test; flagged here as a real follow-up (the fix is the same shape as the two above: call `removeEntityFromIndex("lorebook_entry", id)` from the delete handler) rather than bundled into this pass, which was scoped to freshness-on-write, not the delete path.

**Agent Framework — direction recorded now, not implemented.** The longer-term goal is a background layer that keeps the RAG index fresh, runs scanners without manual triggers, does light DB housekeeping, and accumulates a per-writer/per-project memory the assistant can draw on across sessions. Rather than invent new primitives, the design deliberately reuses what's already in the codebase:
- **One `agentJobs` table, generalizing the existing `ragScans` precedent.** `ragScans` (`status: running|completed|failed` + progress polling, driven by a fire-and-forget async IIFE in `ragScanner.ts`'s `scanStory`) is already the only async/background-job pattern anywhere in `server/`. The generalized table would carry `jobType` (`rag_scan_chapter`, `reconcile_index`, `prune_history`, future types), a polymorphic `storyId`/`entityId` scope, `payload`/`result` JSON, and timestamps — `ragScans`/`ragScanIssues` becoming one `jobType` among several instead of a one-off table.
- **An in-process poller (`jobRunner.ts`), not new infra.** No queue library, `worker_threads`, or cron exists anywhere in this codebase today, and the app is a single Docker container against one SQLite file (`docker-compose.yml`: 2 services, app + languagetool) — a second process contending for the same DB file adds risk with no real benefit at this scale. The runner would claim `queued` rows via an atomic status-flip and requeue anything left `running` after a crash/restart, which the current fire-and-forget `ragScanner.scanStory` pattern can't do (a scan dies silently if the server restarts mid-run).
- **Agent memory rides the existing RAG pipeline instead of a parallel one.** Extending `RagEntityType` (currently `"lorebook_entry" | "chapter"` in `ragRepository.ts`) with `"agent_memory"` means distilled facts about a project or writer become ordinary `ragChunks` rows, retrievable through the same `hybridSearch` — no new retrieval mechanism to build or maintain. Cross-project memory would reuse the nullable-`storyId`-means-global convention `prompts`/`aiChats` already established, rather than a new global/scoped split.
- **Endpoint routing needs no new mechanism.** `buildClientForFeature`'s per-feature override system (already resolving distinct endpoints for `rag_scanner`, `embedding`, `humanizer`, etc., per CLAUDE.md's "writing model and scanner model can run on different machines" requirement) just needs new `FeatureKey`s added when the runner is actually built — zero infrastructure changes.

None of `agentJobs`, `jobRunner.ts`, or the `agent_memory` entity type exist yet. This section records the committed shape so later work doesn't build something incompatible with it — it is not a claim that any of it is built.

## Lorebook Image Support — Manual Upload & AI Generation (Both Built)

**Original decision:** Lorebook entries had no image field — name/description/category/tags/metadata/codexState were all text/JSON. The user asked about adding portrait/reference images (prompted by importing a PDF character sheet whose actual content is ~1 page of text plus ~67 pages of reference images, which the import feature correctly ignores — see "Multi-format Lorebook Import" above). Built as two capabilities, in order:

1. **Manual image upload — built.**
2. **AI-generated images — built.** The AI Settings model catalogue already lists real Grok image-generation models (`grok-imagine-image`, `grok-imagine-image-quality`) once Grok OAuth is connected. The integration shape is genuinely different from every existing AI feature here — `buildClientForFeature`'s whole pattern (`server/services/aiClientFactory.ts`) is built around `client.chat.completions.create(...)`; xAI's image generation is a different, separate endpoint (`POST {baseURL}/images/generations`, confirmed against xAI's own docs rather than assumed, since getting the shape wrong would waste a real billed call) not exposed through the `openai` npm SDK's typed `images.generate()` at all. An explicit user-triggered action ("Generate from Description" button reading the entry's own saved description as the prompt), matching this app's established pattern for every other AI action (Humanizer, Beat Detection, Outline Generation are all opt-in buttons, never automatic) — not something that fires on save automatically.

### Manual upload — implementation

**Storage lives under the existing SQLite DB's Docker volume, not a new one.** New `data/uploads/lorebook/` directory, resolved the same way `DATABASE_PATH` already is in `server/db/client.ts` (`process.env.UPLOADS_DIR || path.join(process.cwd(), "data", "uploads", "lorebook")`) — `docker-compose.yml`'s `${DATA_PATH:-./data}:/app/data` volume already covers it, zero new Docker config needed. New `server/services/lorebookImageStorage.ts` owns filename generation (`{randomUUID}.{ext}`, extension derived from an allowlisted mimetype — jpeg/png/webp/gif only), saving, and best-effort deletion.

**Served through an authenticated API route (`GET /api/lorebook/:id/image`), not a public `express.static` mount.** `server/index.ts` only ever serves static files for the production SPA build. A bare public static mount for uploads would reopen the exact gap the Basic Login entry above already called out and closed ("protecting only two route groups... would be a false sense of security") — this is a private writing tool, character portraits shouldn't be reachable without a session. Browsers send the session cookie automatically on same-origin `<img src>` requests, so this needed no special frontend handling — confirmed by testing `<img>` tags in the real app load correctly while a direct unauthenticated `curl` to the same URL correctly gets a 401. `res.sendFile` handles Content-Type detection automatically from the file extension, no manual mimetype map needed.

**Three new routes in `server/routes/lorebook.ts`** (which already had a multer instance and a `customRoutes` extension point from the earlier document-import work): `POST /:id/image` (upload/replace — deletes the previous file first if one exists, so replacing never orphans a file), `GET /:id/image` (stream), `DELETE /:id/image` (remove without deleting the entry). Also **a custom `DELETE /:id` override** (registered in `customRoutes`, taking precedence over the generic CRUD delete per `server/lib/crud.ts`'s "custom routes first" ordering — same trick `server/routes/outline.ts`'s own delete override already uses) that deletes the image file before the row, so deleting an entry doesn't orphan its image — built in now rather than becoming a second version of the already-documented "delete doesn't clean up RAG chunks" gap.

**Deferred-until-save on the frontend, same pattern `codexState` already established.** `CreateEntryForm` gained `imageFile?: File | null` — `undefined` means no change, a `File` means a new upload, `null` means explicit removal — applied in `LorebookEntryEditor.tsx`'s `handleSubmit` after the base entry create/update succeeds, using the same `entryId = entry?.id ?? randomUUID()` sequencing already in place for Codex state. **`lorebookApi` was extracted into its own `lorebookClient.ts`** (same reasoning as `codexApi`/`ttsApi`/etc. before it — `client.ts` was already over the project's line limit and this feature was about to add two more functions to it) while adding `uploadImage`/`removeImage`/`imageUrl`.

## Chat Context Anchoring: Ground World-Building Chats in the Entry + Project

**Problem, confirmed by tracing the code (not assumed):** opening a World-Building chat from a specific Lorebook entry (e.g. "Elena Cross," via the docked panel in `LorebookEntryEditor.tsx`) gave the AI almost no reliable grounding. Chat creation only stored `storyId`/`chatType`/`templateSlug`/`title` — nothing linked the chat back to the entry it was opened from. `chatContextService.ts`'s `getChatContext` did one RAG hybrid search seeded by the chat's generic template title (e.g. "Character Development," not the entry's actual name), once, on open, never refreshed — whether the entry itself surfaced was down to semantic-similarity luck. `LorebookEntry.metadata.relationships` (a real, already-existing field) was never read anywhere in this path, so declared character connections were invisible to the AI. Separately, `stories.synopsis` (shown on the dashboard card) was never injected into any chat's context, despite being a zero-cost source of baseline project grounding. This is request-time context assembly, not agentic/background work — unrelated to the separately-recorded, deliberately-not-yet-built Agent Framework above.

**Fix — three layers, in priority order:**
1. **Always-on project baseline**: `story.synopsis` now injected into every story-scoped chat's context unconditionally (Editor chats included, not just World-Building — no reason writing assistance should have less project grounding).
2. **Anchor entry**: new nullable `aiChats.anchorEntryId` column. `WorldBuildingChatPanel` (`LorebookEntryEditor.tsx`) threads the entry it's docked to through chat creation (`WorldBuildingChatPanel` → `useCreateChatMutation` → `chatsApi.create` → `POST /api/chats` → `createWorldBuildingChat` → `chatRepository.createChat`, one new optional field at each step, pure pass-through). `getChatContext`'s new `resolveAnchorAndRelated` fetches that entry directly — full current description, not a RAG excerpt — and includes it unconditionally, tagged `role: "anchor"`. A brand-new unsaved entry has no id yet, so this degrades to no anchor with zero special-casing (matches "only for non-new entries").
3. **One-hop relationship walk**: if the anchor entry has `metadata.relationships` (`{targetId, type, description?}[]`), those targets are resolved to their current name/category/excerpt too, tagged `role: "related"` — so "who is this character connected to" is a direct lookup, not RAG luck. Stale targets (entry since deleted) are silently skipped.

`ChatContextCodexEntry` gained a `role: "anchor" | "related" | "search"` field so `resolveCodexEntries` (the existing RAG-result resolver, now taking an `excludeIds` set to avoid double-listing) tags its own results `"search"`. `ChatContext` gained `projectSynopsis: string | null`. `ChatInterface.tsx`'s context-assembly effect (still keyed on `[selectedChat.id]` only, unchanged) formats these into distinct sections — "Focused entry (treat as current, authoritative)," "Entries connected to the focused entry," "Other relevant Codex entries," "Project synopsis" — instead of one flat list, and a small "Focused on: {name}" line renders in the chat header so anchoring silently failing (e.g. the entry gets deleted mid-conversation) is visible to the user rather than just an unexplained drop in the AI's apparent knowledge.

**Explicitly deferred**: per-message RAG re-seeding (using recent conversation content instead of the static chat title as the search query). The `query` param plumbing already exists end-to-end and needs no changes, but re-seeding is its own design problem (what counts as "recent," per-message latency/cost) orthogonal to fixing the anchor-vs-luck problem this pass targets — and this pass's `role` tagging is actually a prerequisite for doing it cleanly later (only `search`-role entries would ever need to churn mid-conversation).

**A real bug found and fixed mid-implementation, not just a design footnote:** the original plan called for `anchorEntryId.references(() => lorebookEntries.id, { onDelete: "set null" })`, based on this file's own `concreteBeats.characterId`/`outlineItems.parentId` comments claiming "SQLite foreign_key enforcement off database-wide." **That claim is false for this connection** — confirmed live via `db.pragma('foreign_keys', { simple: true })`, which returned `1`; `better-sqlite3` defaults FK enforcement ON, and nothing in `server/db/client.ts` ever turns it off. Worse, even with `onDelete: "set null"` declared, SQLite's `ALTER TABLE ADD COLUMN` syntax doesn't support inline `ON DELETE` clauses at all — confirmed by generating the migration and comparing its actual output against every other `ALTER TABLE ADD`-style FK migration in this repo's history (`0016_concrete_beats_character_ref.sql` included), none of which ever emit one despite their schema declaring `onDelete`. First live test (delete an entry that's an active chat anchor) reproduced exactly this: a 500 `FOREIGN KEY constraint failed`, not the intended graceful null-out. **Fixed by dropping the `.references()` call entirely** — `anchorEntryId` is a plain, unconstrained `text` column (still indexed), matching the exact precedent `outlineItems.parentId` already established in this same file for the identical reason ("a self-ref requires an awkward forward-declared callback for no real benefit here; cleaned up in application code instead"). `resolveAnchorAndRelated` already degrades gracefully on a missing/stale anchor id, so application-level handling was already correct — the schema-level constraint was the actual bug, not a missing safety net. **Flagged, not fixed here (pre-existing, out of scope for this pass): `concreteBeats.characterId` likely has this exact same latent bug** — same `ALTER TABLE ADD ... REFERENCES ... { onDelete: "set null" }` pattern, same confirmed-on FK enforcement, so deleting a Lorebook entry that's referenced by any `concreteBeats` row would plausibly also 500 instead of nulling out. Not verified directly (out of scope for this pass), but the mechanism is identical and worth checking before it surprises someone.

## Agent Framework — Phase A (Agent Jobs), Load-Bearing Decisions

**Supersedes this file's earlier "RAG Index Freshness ... & Agent Framework Direction" section's Agent Framework portion** (the `ragScans`-generalization shape recorded there is kept; every gap it left open — scheduling trigger, concurrency model, retry/dead-letter policy, memory write/staleness policy, user visibility, job status surface — is filled by `docs/Agent_Framework_And_Project_Memory_Design.md`, a design spec from Hermes). This entry records the load-bearing choices made while implementing that spec's Phase A (jobs only — no `agentMemories`, which is explicitly Phase B and gated on a separate review).

**New `agentJobs` table** (`server/db/schema.ts`) generalizes `ragScans`: `jobType`, `status` (`queued`\|`running`\|`completed`\|`failed`), nullable `storyId` (real FK, `onDelete: cascade` — a single parent table, and this is a brand-new `CREATE TABLE`, not a later `ALTER TABLE ADD COLUMN`, so the FK's `ON DELETE` clause is preserved correctly), a loose (no-FK) `entityId` for polymorphic scoping, `payload`/`result`/`progress` JSON columns, `attempts`/`maxAttempts` (default 3), and full lifecycle timestamps. `entityId`'s no-FK convention matches `aiChats.anchorEntryId`/`outlineItems.parentId`'s established precedent — worth noting this is the first table applying that convention at creation time (where a real FK would technically have worked) rather than inheriting it from the `ALTER TABLE` limitation those two columns hit; it's still avoided here since `entityId` genuinely spans multiple target tables (chapter or lorebook entry) depending on `jobType`.

**`jobRunner.ts` is strictly serial, in-process, no new infra** — one `setInterval` claim-and-run tick (~3s) and one schedule tick (~60s), matching the single-Docker-container/single-SQLite-file constraint. `agentJobsRepository.ts` is a hybrid: most operations are ordinary async Drizzle (matching every other repository in this codebase), except `enqueue`'s dedup-check-then-insert and `claimNextQueuedJob`'s claim, which use raw synchronous `better-sqlite3` in a `sqlite.transaction()`/single atomic `UPDATE ... WHERE id = (SELECT ...) RETURNING *` — the same reasoning `ragRepository.ts` already established for its own transactional operations (true atomicity in a single-threaded process, not achievable through Drizzle's own await-yielding query builder for a check-then-write).

**Landmine discovered and fixed this session, worth remembering for any future raw-SQL work against a Drizzle-defined table:** Drizzle's `integer(col, { mode: "timestamp" })` columns store epoch **seconds**, not milliseconds (confirmed by reading `drizzle-orm/sqlite-core/columns/integer`: `mapToDriverValue` does `Math.floor(date.getTime() / 1000)`, `mapFromDriverValue` does `new Date(value * 1000)`). The raw-SQL paths above (`enqueue`'s insert, `claimNextQueuedJob`'s update) initially wrote `Date.now()` (milliseconds) directly into `createdAt`/`queuedAt`/`startedAt`/`lastAttemptAt` — passing entirely through, since raw `better-sqlite3` calls bypass Drizzle's serialization. Every *raw-SQL-written* row read back correctly via *other raw-SQL* reads (internally self-consistent, which is exactly why a synthetic unit test comparing raw-written rows only against each other didn't catch it), but any read through **Drizzle** (`getJob`, `listJobs`, or the `/api/agent/jobs*` routes built on top of them) multiplied the already-millisecond value by 1000 again, producing dates around the year 58508. Caught only by live end-to-end verification through the real Settings UI, not by the repository-level test. Fixed with explicit `toEpochSeconds`/`fromEpochSeconds` helpers in `agentJobsRepository.ts` at every raw-SQL read/write site. **Takeaway: any new raw-SQL code touching a Drizzle `mode: "timestamp"` column must convert through epoch seconds by hand — there is no shared helper for this yet, and Drizzle's own conversion is invisible unless you go looking at its source.**

**`rag_scan_story` is deliberately never auto-enqueued by the schedule tick in Phase A.** The design doc's "unattended scan policy: default OFF" (§3.4) has no per-story opt-in setting yet, and adding one is out of scope for this phase — omitting the job type from the schedule tick's periodic list makes "default OFF" true by construction rather than by a setting that doesn't exist. The only way a `rag_scan_story` (or `rag_scan_chapter`) job gets created in Phase A is the manual `POST /api/agent/jobs` route.

**`/api/agent/jobs` is mounted with `requireOwner`**, matching `/api/admin`/`/api/ai`/`/api/users`. This needed an explicit call since `/api/rag` (the closest existing precedent, and what scan jobs still write through underneath) is only `requireAuth`-gated with no owner check — no single existing route family settles this unambiguously. Reasoning: agent jobs are system-level infrastructure that can trigger LLM spend and story-wide reindexing, which a `viewer`/`editor` has no legitimate reason to invoke directly.

**Scan-as-job uses the dual-write/adapter approach the design doc names as recommended short-term** (§3.1): `ragScans`/`ragScanIssues` remain the sole source of truth for scan progress/issues — zero schema or behavior change to `ragScanRepository.ts`, zero risk to the existing `GET /api/rag/scan/:scanId` polling contract. `agentJobs` is a second, thinner wrapper row whose `result` references the underlying `ragScans.id`. `server/routes/rag.ts`'s `POST /scan/chapter/:id`/`POST /scan/story/:id` are unchanged, still calling `scanChapter`/`scanStory` directly — nothing in the frontend calls either route today, so there was no compatibility reason to route them through the job queue instead. `ragScanner.ts` gained three purely additive changes to support the job-runner-driven caller (`server/services/jobs/ragScanJobs.ts`): `runChapterScan` and `requireScannerConnection` exported (were private), and a `listOrderedChapterIds` helper extracted from `scanStory`'s own body (`scanStory` itself now calls it too — its fire-and-forget IIFE, signature, and behavior are otherwise untouched). **This fixes the exact weakness this file called out earlier** ("a scan dies silently if the server restarts mid-run") but only as crash *visibility*, not resumption — a requeued `rag_scan_story` job restarts the whole chapter loop from the beginning, it does not pick up mid-story. Verified for real: a `reconcile_index` job survived an actual `kill -9` mid-run during this session's testing (not staged — a leftover process from an earlier ad-hoc test) and was correctly requeued on the next boot (`jobRunner: crash recovery — requeued 1, permanently failed 0`), then ran to completion.

**Also fixed alongside `reconcile_index` (Step A3), a confirmed live bug, not just a design-doc gap:** `server/routes/lorebook.ts`'s `DELETE /:id` deleted the entry's image file and DB row but never called `removeEntityFromIndex`, permanently orphaning `ragChunks`/`vec_chunks`/`fts_chunks` rows on every lorebook entry deletion (`ragChunks` has no real FK to `lorebookEntries` — loose `entityId` column — so nothing cascaded). Both `POST /` and `PUT /:id` in the same file already called `indexLorebookEntry` on create/update; only the symmetric delete-side cleanup was missing. Fixed with one `removeEntityFromIndex("lorebook_entry", req.params.id)` call. Verified live: created a real lorebook entry via the API, confirmed a `ragChunks` row existed, deleted the entry via the real `DELETE` route, confirmed the chunk row was gone. `reconcileIndexJob.ts`'s orphan pass (comparing indexed `ragChunks` keys against live `lorebookEntries`/`chapters`) is the backstop for any pre-existing orphans from before this fix, or any future delete path that forgets the same call — it does not replace the fix at the source.

**Verified end-to-end against the real dev server and DB, not just synthetic tests**: a standalone script exercised every `agentJobsRepository.ts` function directly against the dev DB (enqueue+dedup, claim, complete, `recordJobFailure` through both the requeue and permanent-fail branches, `retryJob`, `recoverCrashedJobs` through both branches, `listJobs` ordering) before the timestamp bug above was found and fixed by the *next* layer of testing. ## Agent Framework — Phase B (Project Persistent Memory), Load-Bearing Decisions

Implements `docs/Agent_Framework_And_Project_Memory_Design.md` §4 (Steps B1–B5) on top of the stable, committed Phase A (`agentJobs`/`jobRunner`). New `agentMemories` table: factual project knowledge that a background job can only ever *propose* into (`status: pending`) — a human approval is the only path to `active`, and only `active` rows are ever indexed or retrievable. Mirrors this codebase's existing Codex propose→approve flow (`codexPendingChanges`/`codexService.ts`) where the shape fits, diverges deliberately where the design doc calls for something simpler.

**No separate snapshot table, unlike Codex.** Codex pairs every live-entity mutation with an append-only `codexSnapshots` row for history. `agentMemories` instead versions purely through `memoryKey` + status transition: approving a row whose `memoryKey` already has an `active` row atomically flips that previous row to `superseded` (never deleted, just de-indexed) in the same `sqlite.transaction()` as the activation — one raw-SQL function, `agentMemoriesRepository.ts`'s `activatePendingAndSupersede`/`insertActiveAndSupersede`, both sharing an internal `supersedeActiveForKey` step. Verified for real: seeded two pending rows sharing a `memoryKey`, approved the first (`ragChunks` row created, `entityType: "agent_memory"`), approved the second — response's `superseded` object correctly showed the first now `status: "superseded"`, and a direct DB check confirmed the first's `ragChunks` rows were gone while the second's existed.

**Repeated the exact epoch-seconds landmine from Phase A, deliberately guarded against this time.** `agentMemoriesRepository.ts`'s raw-SQL supersession transition writes/reads timestamps the same way `agentJobsRepository.ts` does — copied its `toEpochSeconds`/`fromEpochSeconds` helpers verbatim rather than re-deriving them, specifically because Phase A only caught the "Drizzle's `mode: timestamp` stores epoch seconds, not milliseconds" bug via live testing after a synthetic unit test missed it. Verified live this time before it could surface as a bug: approved memories' `createdAt`/`approvedAt`/`updatedAt` all read back as real 2026 dates through the actual API, not a `+058508` garbage year.

**`hybridSearch`'s new `entityTypes` filter is asymmetric between FTS and vec, and this is deliberate, not an oversight.** `vec_chunks` declares `storyId` as a sqlite-vec `PARTITION KEY` (confirmed by reading migration `0009_rag_vector_search.sql`) but `chunkId` is only a plain auxiliary column — combining an arbitrary `chunkId IN (subquery)` filter with `MATCH ... AND k = ?` is not a construct sqlite-vec is documented to support, so it was not attempted. The FTS candidate query gets a real subquery filter (`fts_chunks` is a standalone table with no such restriction); the vec side stays filtered only by `storyId` as before, with `entityType` filtering applied at the existing metadata-hydration step instead. Accepted tradeoff, stated in the function's own comment: a restrictive `entityTypes` filter can occasionally return fewer than `limit` results if excluded-type chunks occupied ranked vec slots — never affects the default (unfiltered) path every existing caller uses. Verified live: a query matching an approved memory's body returned zero results with `entityTypes` omitted, and returned the memory when `entityTypes` explicitly included `"agent_memory"` — both via the real `POST /api/rag/search` route (this dev environment has no embedding endpoint configured, so this ran the FTS/keyword path specifically, which is also the path with the real subquery filter — the vec-side hydration-time filter path is exercised the same way whenever an embedding endpoint is configured, not separately re-verified here).

**`reconcileIndexJob.ts` (Phase A, already shipped) required a real fix, not just a design-doc nice-to-have.** Its orphan-detection pass only ever recognized live `lorebookEntries`/`chapters` as valid RAG-index keys — every approved `agentMemories` row's indexed chunks would have looked orphaned to the very next `reconcile_index` run and been deleted. Fixed by adding a third `validKeys` source: active memories for the story. Verified live, not just by reading the diff: with an approved, indexed memory in place, manually triggered `reconcile_index` for its story and confirmed the job's own result (`orphansRemoved: 0`) plus a direct `ragChunks` query — the memory's chunks survived.

**`distill_memory` is never auto-chained after a scan job completes, and no dedicated "Suggest memories" UI was built.** No job handler in this codebase enqueues a follow-up job today (only two `enqueue()` call sites exist: the manual route and the schedule tick) — auto-chaining an LLM-calling job after another job would be new, untested territory, and risks the same "background LLM spend must not surprise the user" problem Phase A's `rag_scan_story` guardrail exists to avoid. `distill_memory` is only enqueueable through the existing generic `POST /api/agent/jobs` route (`entityId` reused to hold the source `ragScans.id`, same convention `rag_scan_chapter` already established for a chapter id — no schema change needed). A dedicated trigger button is explicitly Phase C ("do not build now" per the design doc's own §5) and was not built.

**`agentMemories` approval/CRUD is Codex-level auth (`requireAuth` + `blockViewerMutations`), not owner-only like `/api/agent/jobs`.** Memory approval is an editorial decision analogous to Codex proposal approval (editor-allowed today), not system administration. The design doc doesn't specify a restriction; this was the closer existing analogy to follow, made explicitly rather than defaulting to the nearer-by-file-location `/api/agent/jobs` precedent.

**A real Edit-before-approve UI was built, completing a pattern Codex left half-finished.** Codex's backend has supported revising a pending change in place since it was built (`codexRepository.ts`'s `revisePendingChange`, exposed via `PATCH /api/chats/:chatId/codex-proposals/:id`) but has zero UI wired to it anywhere (`useReviseProposalMutation` has no call sites, confirmed via repo-wide grep — `ProposalCard.tsx` only ever renders Approve/Reject). The design doc explicitly requires "Approve / Reject / Edit" for memories, so `ProjectMemoryList.tsx` builds a real inline edit control (title/body/category, `memoryKey` deliberately non-editable) with its own Save button, separate from Approve — a pending row's content edit and its status promotion remain two distinct clicks, matching the design doc's literal three-verb phrasing rather than merging them into one action.

## Project Saves — Phase 1 (Codex Layer: Restore + Timeline UI)

**Decision:** `CLAUDE.md` names "Project Saves split into Codex + Story layers with separate visual timelines" as roadmap item 9, but that one line was — confirmed via three parallel explorations before any code was written — the entire spec that has ever existed for this feature: no design doc, no prior git history, no archived planning docs. Given the real scope (two genuinely separate save systems, two timeline UIs) and no Hermes-style spec to lean on for the edge-case decisions the way Agent Framework Phase A/B had, this was scoped down with the user first via three direct questions rather than guessed at: **Codex layer first** (the Story/chapter layer — `chapters` has zero versioning of any kind today, and autosave destructively overwrites content every ~1s — is a deliberate, separate future phase, not started here), saves are **hybrid** (automatic snapshot creation, which already existed via `codexSnapshots`, plus optional manual naming, which didn't), and restore is **per-item** (one Codex entry at a time, matching how `codexSnapshots` already works — not a whole-project rollback bundling multiple entries).

**The investigation also found `CLAUDE.md` was describing a feature that didn't fully exist.** `codexSnapshots` (append-only, per-entry, auto-created on every create/enable/state-change/approve) was real and working, but restore was not implemented anywhere — no `restoreSnapshot` function, no route — despite `CLAUDE.md` line 26 claiming "Supports per-entry snapshot history with restore capability." Worse, `GET /api/codex/:entryId/snapshots` had zero frontend callers at all — `codexClient.ts` never called it, no component rendered it — so the append-only history table has been silently accumulating real data since the Codex feature first shipped with nothing in the app ever showing it to a user. This phase's actual work was: add the missing restore, add optional labeling, and build the timeline viewer that never existed.

**Restore is itself non-destructive, not a rewind.** `restoreSnapshot` (`server/services/codexService.ts`) applies a target snapshot's `description`/`codexState` to the live entry via the same `updateCodexEntryFields` every other mutation path already uses, then takes a **new** snapshot of the result tagged `sourceType: "restore"` with `sourceRef` pointing back at what was restored from. The restore action is therefore visible in the timeline as its own event and is itself restorable — consistent with `CLAUDE.md`'s "Strong user control and non-destructive history" constraint, and directly verified live: restoring a real demo entry's snapshot took the snapshot count from 3 to 4, not down to a truncated history.

**A real, pre-existing gap in what `codexSnapshots` tracks, surfaced rather than silently worked around:** the table has only ever captured `description` and `codexState` — never `tags` or `needsFleshingOut`. Restore can therefore only restore what was actually snapshotted; a restored entry's tags/needsFleshingOut reflect whatever they currently are, not the tagged state at snapshot time. Fixing this would need its own schema change (both `CreateSnapshotParams` and every one of the four existing snapshot-creation call sites would need to start passing those fields) and was out of scope for what was asked — recorded here so it isn't rediscovered as a surprise later.

## Lorebook Relationship Graph — Library Choice, Source-of-Truth, and Load-Bearing Decisions

Implements `docs/Thin_Story_Graph_And_Lorebook_Visualization.md`'s Phase G1 in one pass: `storyGraphEdges` as the source of truth (not a throwaway metadata-only UI), with the existing `lorebookEntries.metadata.relationships[]` data migrated in and left read-only afterward. Nodes are lorebook entries only; edges are a 15-value concrete/factual allowlist (`knows`, `allied_with`, `opposed_to`, `member_of`, `located_in`, `owns`, `holds`, `works_at`, `related_to`, `part_of`, `caused`, `involved_in`, `mentions`, `contradicts`, `other`) — deliberately no psychological or power-dynamic types, per both the design doc and `CLAUDE.md`'s standing "keep psychological/thematic enforcement out of scope" constraint. **Library choice: `@xyflow/react` (React Flow), a new dependency.** Confirmed via exploration that zero graph-rendering libraries existed anywhere in this codebase before this. Unlike the dependencies this project has previously chosen to avoid (bcrypt/argon2 native bindings, `sharp`, a queue library — see the `README`'s/earlier `DECISIONS.md` entries' reasoning), pan/zoom/drag-to-connect/edge-routing for an interactive node-link graph is the actual value of this feature, not incidental plumbing around a simpler hand-rolled alternative. `@xyflow/react` has no native bindings (no Docker/cross-platform build risk) and is isolated into its own `vite.config.ts` `manualChunks` entry (`"story-graph": ["@xyflow/react"]`, mirroring the one existing `react-markdown` split) so non-graph-tool users never load it.

**`storyGraphEdges` is a brand-new `CREATE TABLE`, not an `ALTER TABLE`, so its `storyId` FK's `ON DELETE cascade` clause is preserved correctly** (the same landmine class already documented in this file for `anchorEntryId`). `fromId`/`toId` are deliberately loose columns with no real FK — entries can be global/series/story-scoped, matching `aiChats.anchorEntryId`/`agentJobs.entityId`'s established precedent. **The partial unique active-edge index was verified to actually work, not just assumed**: `uniqueIndex("storygraphedge_unique_active_idx").on(storyId, fromId, toId, edgeType).where(sql`status = 'active'`)` was checked two ways after `npm run db:generate` — the generated `.sql` file has a genuine `WHERE status = 'active'` clause (not silently dropped), and a live `PRAGMA index_list` against the migrated dev DB confirmed `"partial": 1`. **A real, pre-existing bug was found during exploration that raises the stakes on migrating now, left unfixed and out of scope, but recorded so it isn't rediscovered as a surprise:** `LorebookEntryEditor.tsx`'s save path unconditionally writes `metadata.relationships: []` on every entry save, and `PUT /api/lorebook/:id` does a non-merging overwrite of the whole `metadata` JSON column — so editing any entry through the normal UI silently destroys its legacy relationships. No UI anywhere lets a user view or edit `metadata.relationships` (it was populated only by JSON import or seed data), so this has been a live, silent data-loss bug the whole time this field has existed. ## Document Import — Page-Break Leak, Description-Stripping Prompt, and DOCX Image Extraction, Load-Bearing Decisions

**Decision:** Fixed three real bugs in `documentImportService.ts` (the "upload a PDF/DOCX character sheet, get an AI-extracted draft entry" pipeline), reported by the user after importing a real reference document: the embedded photo didn't come through, physical-appearance prose was missing from the resulting Description even though the same facts correctly landed in Codex state, and literal page-break artifacts leaked into the extracted text.

**Page-break leak was a real `pdf-parse` behavior, not application code, and was root-caused rather than patched around.** `parser.getText()` was called with no arguments; `pdf-parse`'s internal `setDefaultParseParameters` sets `params.pageJoiner ??= '\n-- page_number of total_number --'` when the caller passes nothing, inserting a literal `-- 1 of 3 --` style marker between every page's text — mid-sentence, not at a paragraph boundary. Confirmed this isn't theoretical: ran the real fix against the user's own 68-page reference PDF (`G:\comfy\Character Profile_...pdf`, the same file used earlier this session) and found the marker sitting directly inside a sentence ("...5'4" 105 lbs\n\n-- 1 of 3 --\n\n● Physique: Vex is exceptionally thin..."). Fixed by passing `{ pageJoiner: "" }` explicitly — `??=` only falls back on null/undefined, so an explicit empty string sticks, and `getText()`'s own join loop treats a falsy `pageJoiner` as "just join with a blank line, no marker." Re-ran against the same real PDF and confirmed zero markers remain anywhere in the extracted text.

**Description-stripping was a deliberate prompt instruction, not a separate post-processing step — there was nothing to "un-strip," just a rule to reverse.** `toDraft()` copies the LLM's `description` field verbatim; the system prompt explicitly told the model "Do NOT put physical/wardrobe details here," so the model complied and left description as personality/backstory-only, exactly as instructed — never true removal of anything that existed. Changed the rule to the opposite: description should be the full narrative profile in flowing prose, physical/wardrobe details included, explicitly telling the model not to omit them just because they're also captured in the structured `wardrobe`/`appearance`/`wounds`/`items` arrays. This can't be verified without a live LLM call (no `document_import` endpoint configured in this dev environment), so this fix is prompt-only and unverified end-to-end — flagged here rather than silently claimed as tested.

**DOCX image extraction added first with zero new dependencies.** `mammoth.convertToHtml`'s `convertImage` callback (via `mammoth.images.imgElement`) captures the first embedded image as base64 — verified for real: hand-built a minimal valid `.docx` (raw zip + OOXML parts via Python, a tiny embedded PNG) and ran the actual `extractImageFromDocx` logic against it, confirming a correct `data:image/png;base64,...` URL came back with the right length/prefix, and that the surrounding text extraction was unaffected.

**PDF image extraction was initially scoped out, then added after explicitly asking the user, not silently.** `pdf-parse`'s own `getImage()` method exists but only works with the native `canvas` npm package (Cairo bindings) installed — confirmed via `require.resolve` that it wasn't, and this project has repeatedly and deliberately avoided native-binding dependencies for cross-platform Docker-build risk (bcrypt/argon2, `sharp`, per the Lorebook Relationship Graph entry above). Asked the user directly rather than guessing; they chose to add it. `canvas@3.2.3` added to `package.json` (installed cleanly via a prebuilt binary in this dev environment — `require('canvas').createCanvas` verified working immediately, no from-source build needed here). **`Dockerfile` updated in both stages** (builder and production, matching the existing `better-sqlite3` pattern of reinstalling build tools in the production stage too) to add `libcairo2-dev libpango1.0-dev libjpeg-dev libgif-dev librsvg2-dev` — required for `canvas` to build from source on `node:22-slim`, since this minimal base image has none of node-canvas's native deps present and can't rely on a prebuilt binary matching for every target platform. `extractImageFromPdf` picks the **largest** embedded image by pixel area across all pages (not "first found") specifically so a small decorative icon/logo doesn't win over the actual reference photo.

**Data URL → File conversion is synchronous, not a fetch/Blob round trip, so it fits `useForm`'s synchronous `defaultValues`.** `entryFormUtils.ts`'s new `dataUrlToFile` decodes the base64 payload via `atob()` directly into a `Uint8Array` rather than using `fetch(dataUrl).then(r => r.blob())`, avoiding a broader refactor of `getDefaultFormValues`/`useForm` to support async defaults just for this one path. Only applies when `!entry` (a document-import draft, never an existing entry — existing entries' images are already displayed via their own URL, per `ImageUploadField.tsx`'s existing convention).

**Verified for real, not just by reading the diff**: DOCX text+image extraction against a hand-built test file (above); PDF page-marker fix and PDF image extraction both re-verified against the user's actual real 68-page reference PDF (`G:\comfy\Character Profile_...pdf`) — the page-marker fix showed zero markers remaining, and `extractImageFromPdf`'s exact logic correctly picked out the single embedded photo (2048×2048) and saved it to a real file for visual confirmation it was actually the right character photo, not corrupted/garbage data. `tsc --noEmit` clean on both `tsconfig.json` and `server/tsconfig.json`. Full-repo `oxlint` briefly introduced one new warning (a `curly`-style nested-for-loop violation in the first draft of the largest-image-picking logic), rewritten as a `flatMap`/`reduce` pipeline instead — back to the exact same baseline as every prior entry in this file, 28 warnings/1 error, confirming zero new issues anywhere, frontend or server.

Every invalidation call in this feature (`useUpdateIssueStatusMutation`, both trigger mutations, `useScanJobWithInvalidation`) targets the 3-element prefix (no status segment) specifically so switching the Open/Resolved/Dismissed tab always sees fresh data regardless of which tab was active when the mutation fired.

## Story-Layer Chapter Versioning (P0.2) — Load-Bearing Decisions

**Scope correction mid-session, recorded because it changed the whole feature shape.** P0.2 in `docs/CURRENT_BACKLOG.md` was originally scoped (and partially implemented — schema, repository, routes, all discarded) as linear chapter history: auto-snapshot-on-a-timer + restore, directly mirroring Codex's `codexSnapshots`/restore precedent. The user corrected this mid-build: this feature is chat-branching-style alternate drafts, not undo history — a chapter can have several parallel "temp" versions shown as tabs next to the main chapter, created by AI regenerate or manual duplicate, independently editable, and only ever reach the live manuscript via an explicit one-way "compile" action. The two are genuinely different data models (siblings vs. a timeline) and the discarded linear-history code shared nothing with what got built. Confirmed via direct check: the backlog's own reference to a `2026-06-26_Versioning_Branching_Design.md` doc for the "don't conflate with this" warning does not exist in the repo — it was an aspirational placeholder, so there was no prior design surface to reconcile against either way.

**Scoped via 4 direct questions rather than guessed, all answered as recommended-with-edits:** (1) versions created via AI regenerate and manual duplicate, both; (2) flat list, not a branching tree — "temp files to be compiled to the final chapter output"; (3) main chapter is authoritative the whole time, versions are inert until an explicit compile; (4) view/edit in tabs by default, with an optional side-by-side compare toggle rather than always-on diffing.

**New `chapterVersions` table, deliberately unlike `codexSnapshots` in one key way: no `sourceRef`/restore-chain field.** Codex snapshots form a chain (`restoreSnapshot` creates a new snapshot referencing what it restored from) because Codex is linear history. Chapter versions are flat siblings with one one-way exit (compile) — there's nothing to chain. Columns: `chapterId` (FK, cascade), `content` (Lexical JSON, same shape as `chapters.content`), `sourceType` (`'ai' | 'manual'`), `label` (nullable, user-settable at any time — not retroactive-only like Codex's, since a manual "Save Version" moment has an obvious point to ask for a name), `createdAt`/`updatedAt` (versions get their own ongoing edits, unlike Codex's append-only snapshots, so — unlike `chapters`, which has no `updatedAt` at all — this table needed one from day one).

**Compile is genuinely irreversible, not "non-destructive" like the rest of this project's save/history features — called out explicitly in its own confirmation dialog.** It copies a version's content into `chapters.content` with no automatic backup of what's being replaced (`compileVersionToChapter` in `chapterVersionsRepository.ts`). This is a deliberate departure from CLAUDE.md's "non-destructive history" principle for Codex/RAG-scanner-adjacent features, accepted because the user explicitly scoped this phase as not linear undo history — pairing compile with real undo would mean building the P0.2-that-wasn't (chapter snapshots) after all. Worth revisiting if this friction shows up in practice; noted here rather than silently decided.

**Trigger path for AI regenerate mirrors Humanizer, not the streaming "Generate with prompt" path** — non-streaming `buildClientForFeature("chapter_version")` call (new `FeatureKey`), whole rewritten chapter returned in one response with a loading spinner in `GenerateVersionDialog.tsx`. Simpler for a first pass; a multi-thousand-word wait with no progressive feedback is the accepted tradeoff, flagged as a candidate for streaming later if it feels slow in practice.

**A hand-rolled plain-text to Lexical converter (`textToLexicalContent` in `chapterVersionAiService.ts`), not `@lexical/headless`.** The AI service returns plain prose text (via the existing `extractTextFromLexical` reused unchanged for the other direction); turning that back into editable Lexical JSON server-side needed some conversion, and `@lexical/headless` isn't a dependency of this project. Rather than add it for one call site, the exact minimal paragraph-node shape was confirmed by inspecting real stored chapter content directly (`server/data/demo-story-shadows-berlin.json`) and hand-built: split on blank lines into paragraph nodes, one text child each. Deliberately not a markdown parser — good enough for a first AI draft; the user's own editing (bold/italic/etc.) takes over from there.

**Version tabs get a bespoke, deliberately lighter Lexical composer (`VersionEditor.tsx`), not the main editor's `App.tsx`/`Editor.tsx` reused wholesale.** Checked first: `Editor.tsx` hardcodes several plugins — `WordCountPlugin`, the focus-session button in `ToolbarPlugin` — that resolve "which chapter" via `useEditorChapterId()`'s fallback to the global `StoryContext` when no `EditorPaneProvider` wraps them. A version tab isn't (and shouldn't be) wrapped in one, so reusing those plugins as-is would silently report a version's word count, or let a focus session start, against whatever chapter happens to be globally active — wrong data, not just wrong UX. `VersionEditor.tsx` reuses only the content-agnostic pieces (`PlaygroundNodes`, `PlaygroundEditorTheme`, `RichTextPlugin`, `HistoryPlugin`, `MarkdownShortcutPlugin`, `AutoFocusPlugin`) plus a new minimal `VersionToolbar.tsx` (undo/redo/bold/italic/underline only) and forked `LoadChapterVersionContentPlugin`/`SaveChapterVersionContentPlugin` (same debounce/`toJSON` shape as the chapter originals, scoped to a `versionId` instead, with no beat-detection/RAG-reindex side debounces — a draft isn't part of the manuscript yet). Not integrated into `EditorMultiView`'s pane/split/floating-panel/layout-persistence system, despite that system already supporting "two independent live editors side by side" (which the Compare toggle also needed) — grafting a version concept into machinery built for "which chapter is this pane showing" was judged more structural risk than the toolbar duplication it would have saved.

**A real bug found and fixed during live verification, not just assumed away.** `useUpdateVersionContentMutation` (a version's autosave) originally did nothing to the React Query cache on success, on the theory that the actively-focused editor already has the latest content live and doesn't need it reflected anywhere else. This broke the moment a second editor instance for the same version mounted — e.g. toggling Compare — which loads its initial content from `LoadChapterVersionContentPlugin`'s `content` prop, sourced from the (now-stale) cached version list. Confirmed live: edited a version, toggled Compare, and the second pane showed content from before the edit. Fixed by having the autosave mutation's `onSuccess` patch the list cache in place via `queryClient.setQueryData` (not a full invalidate/refetch, which would either do nothing useful for the already-loaded editor or thrash unnecessarily) — mirrors `useUpdateChapterMutation`'s own `setQueryData` pattern in `useChaptersQuery.ts`.

**A separate, pre-existing data-quality issue was found while chasing the above, confirmed unrelated to this feature, and left alone.** `demo-chapter-1`'s own `chapters.content` (not `chapterVersions`) already contains a structurally malformed paragraph — three originally-separate paragraphs collapsed into one text node joined by a literal double-newline, with a stray extra period and an incorrect italic flag — verified directly against `GET /api/chapters/demo-chapter-1` outside of any version. Every new duplicate/generate/save path here faithfully round-trips whatever the source chapter contains, corruption included, without introducing any new corruption of its own (confirmed by a controlled single-character edit test whose save came back byte-for-byte correct apart from the intended change). Root cause not investigated further — it predates this session and sits in the main chapter editor's save path, out of scope for chapter versioning.

**Verified live end-to-end against the real dev server and DB, as the logged-in owner test account:** manual duplicate (toast, new tab, content matches Main, edits fully isolated from Main confirmed by switching tabs both directions), a real AI-generate call with an instruction (`buildClientForFeature("chapter_version")` against this dev environment's actual configured model, roughly 15-20s wait, genuinely different and coherently rewritten prose, correctly split into clean paragraph nodes), the Compare toggle (side-by-side Main + version panes, independently scrollable), Compile (confirmation dialog copy read correctly, real content transfer into `chapters.content` confirmed by switching to Main and seeing the AI draft's text, `["chapters"]` cache invalidation reflected without a manual reload), and Delete (confirmation dialog, tab removed, toast, Main unaffected). `tsc --noEmit` and `oxlint` both clean (extracted `chaptersApi` out of `src/services/api/client.ts` into its own `chaptersClient.ts` file, matching that file's existing per-feature-file precedent, since this feature's one-line re-export addition pushed it over the 250-line cap; fixed an `autoFocus` a11y warning and a `versions` exhaustive-deps warning introduced along the way).

## Chapter Content Undo/Restore (P0.2b) — Load-Bearing Decisions

Implements the backlog item split out after P0.2's scope correction (see the "Story-Layer Chapter Versioning (P0.2)" entry above) — linear undo history for the *main* chapter's own content, mirroring the Codex `codexSnapshots`/restore precedent this time for real. Reused the three scoping answers the user gave earlier in that same corrected session (coarse ~15min auto-checkpoints + manual named saves; unbounded retention like Codex; view/restore only, no diff view) rather than re-asking, since they were answered in service of exactly this feature even though the build that immediately followed went a different direction.

**New `chapterSnapshots` table, closely mirroring `codexSnapshots`** — `id`, `chapterId` (FK, cascade), `content` (Lexical JSON), `sourceType` (`'auto' | 'manual' | 'restore'`), `sourceRef` (the snapshot restored from, or the compiled version id for a pre-Compile safety checkpoint), `label`, `createdAt`. Unlike `chapterVersions` (P0.2, flat siblings, no chain), this table forms a restore chain the same way Codex's does.

**`'auto'` snapshots are throttled server-side (~15min per chapter), computed inside the chapter content `PUT` route itself** — `chapters.ts`'s generic CRUD `PUT /:id` is overridden in `customRoutes` (same override-and-delegate pattern `lorebook.ts` already established) to call `maybeAutoSnapshot(chapterId, oldContent, newContent)` before applying a content change, snapshotting the *old* content once the last snapshot (of any type) is stale enough. Chapters autosave continuously while typing, unlike Codex's discrete per-mutation snapshots, so a naive "snapshot on every save" policy would produce hundreds of rows per session — flagged as a real requirement during P0.2b's scoping and confirmed by measuring real demo content (~18 bytes/word as full Lexical JSON).

**Manual "Save Version" reads the chapter's already-autosaved DB content, not a value pushed from the live editor** — `POST /:chapterId/snapshots` takes no content in its body. Considered threading the live editor's `editor.getEditorState()` through instead (to avoid the ~1s autosave-lag edge case), but the History drawer lives in `EditorToolsPanel.tsx`, a sibling of the `LexicalComposer` tree, with no clean access to the live editor instance without new plumbing — accepted the small lag risk rather than add that.

**Compile (from P0.2) and Restore both now take an unconditional safety checkpoint before their one-way overwrite** — `compileVersionToChapter` and `restoreSnapshot` both call a new `safetySnapshot` helper that bypasses the 15-minute throttle entirely, since these are rare, deliberate, high-stakes actions rather than routine autosaves. This directly closes the gap flagged when Compile shipped in the P0.2 entry above ("a one-way, un-backed-up overwrite... adds one more way to lose the previous state, not fewer"). Restore's confirmation dialog can now honestly say "nothing is lost," matching Codex's own restore copy, instead of inheriting Codex's *implicit* safety (every mutation snapshotted) without actually having it.

**A real ordering bug was found and fixed during live verification**: `chapterSnapshots.createdAt` has the same 1-second resolution as every other timestamp column in this codebase (Drizzle's `mode: "timestamp"` floors to epoch seconds), and both `restoreSnapshot` and `compileVersionToChapter` create two rows back-to-back in one request — easily landing in the same second. Confirmed live: a restore's safety-checkpoint and its result snapshot tied on `createdAt`, and `ORDER BY createdAt DESC` alone returned them oldest-first instead of newest-first (SQLite's default tie-break happened to preserve insertion order, not reverse it). Fixed with a secondary `ORDER BY ..., desc(sql\`rowid\`)` (drizzle-orm's `sql` template tag for a raw column reference) — SQLite's implicit rowid increases monotonically with insertion, giving a reliable tie-break. Confirmed via direct API inspection before and after the fix (`{auto, restore}` order → `{restore, auto}` order).

**The "Current" badge is based on an actual content comparison against the live chapter, not list position** — a real bug caught live before it shipped: `CodexHistoryPanel.tsx`'s precedent marks `index === 0` (newest in the list) as current, which is safe for Codex because every mutation is snapshotted, so the newest snapshot genuinely is always current. Chapter snapshots are throttled, so the live chapter can easily have moved on from the most recent snapshot with no new one created yet — confirmed live: right after a manual save, a further (unsnapshotted) edit still showed the stale save as "Current" under the naive index-based check. `ChapterHistoryDrawer` now takes the chapter's live `content` as a prop (already available via `EditorToolsPanel`'s `currentChapter`) and compares each snapshot's content directly.

**A serious race condition was found and fixed during live verification: Restore (and, by the same logic, Compile) could silently undo itself seconds after succeeding.** The original `refreshChapterContent()` mechanism (added so an already-mounted editor picks up an externally-changed chapter — `LoadChapterContentPlugin`'s "load once per chapterId" gate has no other way to learn this) just bumped a token and relied on `invalidateQueries` to have already refreshed the cached chapter by the time `LoadChapterContentPlugin` re-read it. Confirmed live, repeatedly, before being fixed: the token bump could fire *before* the invalidated query's background refetch resolved, so `LoadChapterContentPlugin` reloaded the editor from the **still-stale, pre-restore** cached content — which then looked like a fresh (dirty) edit and got autosaved right back over the database a second later, permanently reverting the restore with no error, toast, or other visible sign anything had gone wrong. Caught only because a test marker string was checked directly against the DB after the fact, not by watching the UI. Fixed in both `useRestoreSnapshotMutation` and `useCompileVersionMutation` by writing the mutation's own (already-fresh) chapter response straight into the `["chapters", chapterId]` query cache via `setQueryData` *before* bumping the refresh token, removing the race entirely rather than narrowing its window. `chaptersKeys`' own factory isn't exported from `useChaptersQuery.ts`, so both call sites spell out its "detail" key shape directly, matching the precedent already set for the "byStory" prefix elsewhere in this feature.

**Environment note, not a code issue: this session hit a `concurrently`-specific hang on the dev machine.** `npm run dev`'s `concurrently "npm run dev:server" "npm run dev:client"` repeatedly left the server child silently stuck (no boot log, no error, no crash) while the client child booted normally, across multiple full process-tree restarts. Running `tsx watch server/index.ts` directly (bypassing `concurrently`) booted correctly and immediately every time, isolating the hang to `concurrently`'s process handling on this machine rather than the server code. Worked around by launching the server and `vite` as two separate background processes instead of through `concurrently` for the remainder of this session's verification — not a code change, recorded here only so a future session doesn't re-diagnose the same thing from scratch.

**Verified live end-to-end against a genuinely fresh process (both the concurrently hang and, separately, a stale-HMR "hooks order changed" React warning were both ruled out this way — neither reproduced from a clean server+client boot and a real page load, confirming both were session/tooling artifacts, not code bugs):** a manual save, an edit, and a restore all round-tripped correctly with the ordering and "Current"/race fixes in place — confirmed via direct `GET /api/chapters/:id` and `GET /api/chapters/:id/snapshots` checks (not just UI observation, given the race bug above was invisible in the UI) that the restored content stuck and stayed stuck. `tsc --noEmit` (both configs) and `oxlint` clean, back to the exact same 27-warning/1-error baseline as before this session's changes.

## Notes/Outline ↔ Chat Bridge (P0.3, "Core Bridge" scope: N0-N4 + O1-O4) — Load-Bearing Decisions

Implements `docs/CURRENT_BACKLOG.md`'s P0.3 against the locked design in `docs/Notes_Outline_Chat_Bridges_Design.md` (2026-07-18). Scope chosen directly by the user from three options: the full read-side double-gate pipeline for both notes and outline items (schema, RAG indexing, chat toggles, context injection, export/import) — **not** N5/N6 (save-as-note, note-proposal chat UX) and **not** C1-C5 (project-memory chat toggle), both left for a follow-up pass.

**Schema: `notes.includeInAi` / `outlineItems.includeInAi` / `aiChats.includeNotes` / `aiChats.includeOutline`, all `NOT NULL DEFAULT false`** (migration `0033_cultured_magneto.sql`). Frontend `Note`/`OutlineItem`/`AIChat` types mark these fields **optional**, not required, even though the DB column is `NOT NULL` — several existing client call sites construct these objects for `POST` without every field (server fills the default), matching this codebase's existing convention for other server-defaulted fields (e.g. `AIChat.updatedAt?`).

**RAG entity types extended to `"note" | "outline_item"`, staying fully opt-in — never added to `DEFAULT_SEARCH_ENTITY_TYPES`.** Mirrors the exact `agent_memory` precedent from Agent Framework Phase B: new thin `indexNote`/`indexOutlineItem` wrappers in `ragIndexService.ts` (same shape as `indexAgentMemory`), added to `rag.ts`'s `VALID_ENTITY_TYPES` allowlist, and a new valid-keys pass in `reconcileIndexJob.ts` for armed (`includeInAi=true`) rows — no staleness check needed (same reasoning as the `agent_memory` block: routes/notes.ts and routes/outline.ts always reindex synchronously on write, so drift can only mean "should be removed," never "should be refreshed").

## Editor Selection Rework + Codex Proposal Tray (P0.4 R0-R3) — Load-Bearing Decisions

Implements slices R0-R3 of `docs/Chat_Panel_Integrations_Design.md` (§2, §2.1, §3, §9) — the user's chosen starting slice of the much larger P0.4 design (deferred: B0-B5 Brainstorm playbook migration, S0-S5 Research web search, K0-K5 Notes desk polish, and the Editor/Outline `chatType` split, R6-R7). Replaces the floating toolbar's one-shot Expand/Rewrite/Shorten (`selection_specific` prompt, immediate `RangeSelection.insertText()`, no review step) with a chat-bound "Rework in chat" flow, and moves Codex proposals for Editor(/Outline, which shares the same rail) chats out of inline-under-message rendering into a persistent tray.

**A real correctness bug in `activeChapterEditorStore.ts` was found and fixed before building on it, not after.** The store held one global `{chapterId, editor}` slot, reassigned on every pane mount and Lexical `FOCUS_COMMAND` — fine for the existing prose-proposal Accept (happens moments after typing, focus rarely moves away yet) but not for Selection Rework, which is explicitly multi-turn: a user can highlight in chapter A, chat for several turns, quite plausibly focus a different chapter/pane meanwhile, and still expect Accept to find chapter A's editor. Changed to a `Map<chapterId, LexicalEditor>` of every currently-mounted editor (dropping `setActiveChapterEditor`/the `FOCUS_COMMAND` listener entirely — nothing needs "which pane is currently focused," only "is a live editor for this chapter still mounted"). Strictly improves the pre-existing prose-proposal Accept path too, not just the new feature.

**`FocusTarget`/`FocusPacket` capture uses Lexical node keys + offsets, not just plain text** (`src/features/rework/adapters/chapterSelectionAdapter.ts`) — captured once at "Rework in chat" click time, re-resolved at Accept time (potentially many chat turns later) via `$getNodeByKey` + `$createRangeSelection`. A safety check (`selection.getTextContent() === target.text`) guards against the chapter having changed in the meantime.

**Degrade-on-mismatch, not fuzzy-search, when the captured selection no longer resolves cleanly.** If the target's node keys are gone, or the reconstructed selection's text no longer matches what was captured, `applyChapterSelectionReplace` does **not** guess at a different location (e.g. searching for the phrase elsewhere in the chapter) — that risks silently editing the wrong occurrence, which is worse than doing nothing. Instead it falls back to the already-shipped `insertProposedProse` insert-at-cursor-or-end path and returns `"selection-changed"`, surfaced to the user via toast ("...inserted instead of replacing; please check placement"). If the chapter has no mounted editor at all, returns `"not-found"` and the proposal card stays visible so the user can retry after opening that chapter, rather than discarding the model's work. Matches this codebase's established degrade-to-known-state convention (`resolveAnchorAndRelated`/`resolveAnchorChapter` returning `[]` on a stale reference, not guessing).

**No new proposal fence type for rework replies — the existing `prose-proposal` fence is reused, with "replace vs insert" tracked as client-side per-message state.** `docs/Chat_Panel_Integrations_Design.md` §3.3 explicitly allows "extend fence types **or reuse** ... with target metadata," and whether Accept should replace-in-place or insert-new is never something the model needs to encode — `ChatInterface.tsx`'s `proseProposals` state changed from `Record<string, string>` to `Record<string, { text: string; target: FocusTarget | null }>`, snapshotting `activeRework?.target` at the moment `onProseProposal` fires. `handleAcceptProse` branches on `target` presence. Avoided a second parser file, a near-duplicate card component, and a second server-side instructions string to keep in sync with the first. Server-side, `PROSE_PROPOSAL_INSTRUCTIONS` (`chatContextService.ts`) gained one added sentence: when `[SELECTION REWORK]` context is present in the conversation, the fenced block should replace SELECTION only, not repeat BEFORE/AFTER.

**"Rework in chat" resolves to an existing chat anchored to the target chapter if one exists, rather than always creating a new one** — genuinely new UX in this codebase (no prior precedent; World-Building's `anchorEntryId` is write-only metadata for context assembly, never read back for chat *selection*). Zero matches → create; exactly one → select silently; more than one (a user can legitimately have several named Editor chats anchored to the same chapter) → select the most-recently-updated **and** toast `Continuing in "<chat title>"`, since silently guessing which of several conversations to resume is otherwise an invisible decision the user has no way to notice or correct.

**A second real, pre-existing bug was found and fixed while verifying the "resolve to existing anchored chat" flow**: `useCreateChatMutation`/`useUpdateChatMutation` (`src/features/chat/hooks/useChatQuery.ts`) invalidated `chatKeys.byStory(storyId)` — which resolves to the *type-suffixed* key `["chats","story",storyId,"all"]` — on every chat create/update. React Query's `invalidateQueries` only matches queries whose key **starts with** the given key, so this never actually touched any type-specific list query (`["chats","story",storyId,"editor"]`, `"worldbuilding"`, etc. — every real caller in the app). Confirmed live: creating a chat via the new Rework flow correctly selected/displayed it in the main pane (that half doesn't depend on the cache, it uses the mutation's own returned object) but the chat never appeared in the sidebar `ChatList` until a full page reload. This bug predates Rework — it would have equally affected the pre-existing "New Chat" button — but Rework's find-or-create logic depends on the list being fresh for its own "does an anchored chat already exist" check, so it was fixed here rather than left for a future session. Fixed by invalidating the shorter `["chats","story",storyId]` prefix instead, which matches every typed sub-list for that story.

**Environment limitation, not a code issue: could not complete a live end-to-end Accept (real LLM reply → replace selection) in this dev environment.** Confirmed via direct network trace that the generate request reached `POST /api/ai/grok-session/generate` successfully and returned `200 OK`, but the response body was `data: [DONE]` with zero content tokens — the configured SuperGrok session provider isn't actually producing output in this dev environment right now (same category of gap already documented elsewhere this session as "RAG search: embedding unavailable... Connection error" — this machine's AI backend connectivity, not this feature's code). Every other piece of the flow was verified live and worked correctly: selection capture and `ReworkCard` preview (exact captured text shown, correct truncation labels), find-or-create chat binding (both branches — zero-match create and one-match reuse — exercised live against the real DB), the request reaching the server with correct context (confirmed via the `/context` network call), Codex tray rendering (status tabs, empty state), and the "Clear rework" control. `applyChapterSelectionReplace`'s Accept-time logic itself is a direct, carefully-reviewed adaptation of the exact `RangeSelection.insertText()` pattern already proven live elsewhere in this codebase (`FloatingTextFormatToolbarPlugin`'s existing `handleGenerateWithPrompt`/`handleHumanize`), not new/unproven Lexical usage. `npm run build` (tsc client+server+vite) clean throughout.

**A hot-reload gotcha hit again, worth remembering for future sessions**: after adding the `includeMemory` column and reading it in `chatRepository.ts`/`chats.ts`, the already-running `tsx watch` server kept returning chat objects with `includeMemory` silently absent (not `false` — genuinely missing from the response) for several requests, because `tsx watch`'s hot-reload hadn't yet picked up the `schema.ts` change and `db.select().from(schema.aiChats)` was still working from the stale in-memory column list. A full server restart (stop + fresh `preview_start`) fixed it immediately. Same root cause as the earlier import-fix false-negative in the Notes/Outline bridge entry above — if a just-added column/field silently doesn't show up in a response, restart the dev server fully before assuming the code is wrong.

## P0.4 B5 — WB + Outline Guided-Start Playbooks + Character Psych Module — Load-Bearing Decisions

Extends B0-B4's guided-start UX (composer blurb + Guided Setup button + Light/Standard/Grill-me style dropdown, `chatContextService.ts`'s style-hint pattern) to World-Building and Outline chats, plus WB's Character template gets an opt-in psych module (MBTI/Enneagram/freeform blurb, chat-interview-then-propose). Plan locked via `EnterPlanMode` before implementation (same plan file as B0-B4, `zazzy-wishing-cray.md`, overwritten for this slice).

**Research eliminated most of what looked like new architecture before any code was written.** `lorebookEntries.metadata` is already a generic, unvalidated JSON column (already holding `relationships[]`) — `psychProfile` fits there with **zero schema migration**. The generic `PUT /api/lorebook/:id` route already accepts arbitrary body fields including `metadata` with no allowlist — `useUpdateLorebookMutation` already does everything the psych-proposal Accept path needs, **no new server route**. And `CodexPendingChangesPanel`/`CodexHistoryPanel` in `LorebookEntryEditor.tsx` were the exact precedent for a new read-only `PsychProfilePanel` — rendered outside the RHF form, reading straight off the `entry` prop already passed in, no query of its own.

**Psych module deliberately bypasses the Codex pending-change pipeline entirely, not an extension of it.** `codexService.proposeChange`/`approvePendingChange` is architecturally concrete-state-only — every approve takes a `codexSnapshots` row, which is meant to be a history of the entry's *concrete* state. Extending `codexPendingChanges` with a `proposedMetadata` field would have made psych data show up in Codex snapshot history, blurring the project's own standing line (CLAUDE.md: "Character Codex... concrete/physical state only (no psychological modeling)"; "Keep psychological/thematic enforcement out of scope"). The psych module reconciles with that constraint by staying strictly outside it: a **new parallel `psych-proposal` fence**, same posture as `note-proposal` (ephemeral client-side card, never persisted server-side as a pending row), writing directly to `metadata.psychProfile` via the plain entry-update route — never touching `codexState`, `codexPendingChanges`, or `codexSnapshots`. The design doc's own framing ("writing aid only," "not scanner-enforced," "not a continuity 'law' pipeline") is what makes this a narrow, deliberate exception rather than a reopening of that constraint — recorded here explicitly so a future session doesn't mistake this for scope creep on the "no psychological modeling" rule.

**Per-host style hints stay separate text, not shared data, on purpose.** `BRAINSTORM_STYLE_HINTS`/`WB_STYLE_HINTS`/`OUTLINE_STYLE_HINTS` are three distinct `Record<string,string>` maps in `chatContextService.ts` — "propose a short synopsis" only makes sense for Brainstorm, "scene-by-scene goal/conflict/outcome" only for Outline. What's shared is the *pattern* (a small `resolveStyleHint(hints, style)` helper doing the same `hints[style ?? "standard"] ?? hints.standard` fallback for all three), not the content. Same reasoning applies to `GuidedSetupControl.tsx`'s generalization: moved from `features/brainstorm/` to `features/chat/` and reshaped so the **caller** supplies `blurb` and computes the opening line via `onGuidedSetup(style)`, rather than the component owning Brainstorm-specific `OPENING_LINES` — each host (`BrainstormTool.tsx`, `LorebookEntryEditor.tsx`'s `WorldBuildingChatPanel`, `OutlineChatRail.tsx`) now owns its own opening-line map inline. WB's opening lines are deliberately generic per-style (not a 5-template × 3-style combinatorial table) — the blurb line above the control already names the template, so the opening line itself only needs to vary by depth.

**A real correctness bug was found and fixed, affecting B0-B4's `brainstormStyle` too, not just this session's new columns.** `ChatInterface.tsx`'s `codexContext`-fetch `useEffect` never included any style/psych-module value in its dependency array (`[selectedChat.id, includeNotes, includeOutline, includeMemory, includeLorebook, includeChapterSummaries, isBrainstormChat]`) — so changing style or the psych toggle updated the chat row in the DB correctly, but the component's own cached `codexContext` (what's actually sent to the model on the next `generate()` call) stayed stale until something *else* happened to re-run the effect (a different toggle, or a full reload). This silently defeated the entire point of the style/psych controls for one turn after every change. **Caught live** while verifying B5 (toggling "Psych module" produced a `PATCH` with no follow-up `GET .../context`) — confirmed the same gap already existed for `brainstormStyle` since B0-B4, just never surfaced because that session's own verification didn't specifically check for a context refetch after a style change. **Fixed** by adding `selectedChat.brainstormStyle`/`selectedChat.wbStyle`/`selectedChat.outlineStyle`/`selectedChat.includePsychModule` to the effect's dependency array — safe because every caller's `handleStyleChange`/`handleTogglePsychModule` already does `chatsApi.update(...).then(setSelectedChat)`, passing a **fresh** chat object (new field values) rather than mutating in place, so the dependency change is real and the effect refires correctly. Verified live after the fix: toggling the psych switch or the style dropdown now immediately fires a follow-up `GET /api/chats/:id/context`, and the returned `systemPrompt` reflects the new state on the very next check.

**`includePsychModule` is gated on `anchorEntryId` presence, not just the toggle, both server- and UI-side.** `chatContextService.ts`'s `getChatContext` computes `includePsychModule = chat.includePsychModule === true && !!chat.anchorEntryId` before it ever reaches `buildSystemPrompt` — an unanchored WB chat (created via the template picker before saving a new entry, or a freeform chat with no anchor) has nowhere to attach a psych-proposal Accept, so the model is never even told the fence exists in that case, regardless of the toggle's stored value. Verified live: toggling the switch on an unanchored "Character Codex" chat persisted `includePsychModule: true` in the DB (the UI doesn't hide the toggle for unanchored chats — no reason to, it's harmless) but the assembled `systemPrompt` correctly omitted `PSYCH_MODULE_INSTRUCTIONS`; a second chat created anchored to a real character entry with the same toggle on correctly included it (confirmed via `ctx.systemPrompt.includes("psych-proposal")`).

## P0.4 R6 — Auto-insert/Auto-accept Toggles — Load-Bearing Decisions

**Outline auto-accept for `create` changes the row's initial `status`, not a post-creation update.** The pre-existing "create" path (`onOutlineProposals` in `ChatInterface.tsx`) already persists immediately regardless of any toggle — the retired bulk-Generate button's own convention, landing `status: "pending"` and showing an "AI Suggested" badge with Accept/Reject controls (`OutlineChapterCard.tsx`/`OutlineSceneRow.tsx`). So when `autoAcceptOutline` is on, `create` proposals are created with `status: "confirmed"` directly — same end state as an instant manual accept, skipping the badge/review step entirely rather than creating-then-immediately-patching. `edit`/`reorder` reuse the exact same mutations `handleAcceptOutlineProposal` already calls manually (`updateOutlineItemMutation`/`reorderOutlineMutation`), just invoked eagerly instead of being pushed into the ephemeral `outlineProposals` card state. `delete` is excluded via an explicit `proposal.type !== "delete"` guard on the auto-accept branch — always falls through to the ephemeral card regardless of the toggle, matching the design doc's asymmetric table.

## P0.4 S0-S5 — Research Chat Web Desk — Load-Bearing Decisions

The last major unimplemented piece of P0.4's chat/panel integration design (`docs/Chat_Panel_Integrations_Design.md` §6). Research previously had no research-specific behavior at all — it was a single always-Global chat sharing generic `ChatInterface.tsx` plumbing (`showContextSelector`/toggle-row logic all fell through the same `!isEditorChat`/`!isOutlineChat`/`isBrainstormChat` branches every other "none of the above" chat type used).

**A real pre-existing bug was found and fixed as a prerequisite, not a side effect.** `chatContextService.ts`'s `buildSystemPrompt` had no `chatType === "research"` branch, so Research chats silently fell through to the World-Building default — meaning the model was told `WORLDBUILDING_FRAMING` (wrong role) **and** `CODEX_PROPOSAL_INSTRUCTIONS` (letting it propose Codex entries from Research), directly violating the design doc's "Writes: Lorebook/Codex/outline/prose → None." Fixed with a dedicated `RESEARCH_FRAMING` constant — no Codex/outline/prose write instructions, deliberately keeps `NOTE_PROPOSAL_INSTRUCTIONS` (the design's one allowed write) with an added "only on request" qualifier sentence, per §6's "Research Notes | On request."

**Search provider: DuckDuckGo HTML scraping, explicit user choice over a keyed API (Tavily/Brave/SerpAPI).** User picked "ddgs / DuckDuckGo Search" via `AskUserQuestion` — the same site the Python `ddgs` package scrapes (`html.duckduckgo.com/html/`, a JS-free result page built for scraping). No new Settings UI, no `aiSettings` column, no key management at all — the whole point of the choice. New `server/services/webSearchService.ts` (`cheerio` added as a new dependency — pure-JS HTML parsing, no native bindings, consistent with this project's stated native-binding aversion) exposes `searchWeb`/`fetchPage`, both wrapped in try/catch returning `[]`/`null` on any failure — unofficial/best-effort scraping (no SLA, may occasionally rate-limit or serve a CAPTCHA) running inline in the chat-send path must never throw and break message sending. Since this app is self-hosted and requests originate from the user's own residential IP rather than a cloud datacenter IP, it's meaningfully more likely to work reliably than a typical hosted scraper — recorded here as the operational trade-off, not a guarantee. `fetchPage` also unwraps DDG's redirect-wrapped result URLs (`//duckduckgo.com/l/?uddg=<encoded>`) back to the real target.

**Web search is query-driven, not toggle-gated like Notes/Memory/Lorebook — a static per-chat boolean can't know what a given turn is asking about.** `getChatContext(chatId, query?)` already threaded a `query` param for RAG relevance (falling back to `chat.title` when omitted, e.g. the mount-time context fetch every chat type does on load/toggle-change). Reusing that same fallback for web search would fire a live scrape with a nonsense query (the chat's title) on every mount — so a second, stricter `explicitQuery = query?.trim() || null` was added, used only to gate `resolveWebSearch`. The client-side consequence: the existing mount-time `codexContext` effect in `ChatInterface.tsx` (no query passed) never triggers a search; a **new** per-send fetch in `handleSubmit` (`chatsApi.getContext(selectedChat.id, input)`, Research-only) does, using the user's actual outgoing message text. Any `http(s)` URL found in that same query text is fetched too (capped at 2), delivering S1's "page fetch" half through the same call.

**The freshly-fetched search context is threaded into `generate()` as a plain parameter, not routed through React state.** A `setState` immediately before calling `generate()` wouldn't be visible inside `createPromptConfig`'s closure until the next render — a real race that would have silently sent the previous turn's (or no) search context. Instead `useChatMessageGeneration.ts`'s `generate`/`createPromptConfig` signatures both gained an `extraContext?: string` parameter, merged into the existing `[codexContext, reworkContext]` join (now `[codexContext, reworkContext, extraContext]`) — the same "just another optional string source" shape `reworkContext` already established, so no new merge concept, just one more slot.

**A second real bug was caught while restructuring `entityTypes` for Research's "no default search entities" requirement.** `hybridSearch()` (`ragRepository.ts`) builds a SQL clause via `entityType IN (${entityTypes.map(() => "?").join(",")})` — with an empty `entityTypes` array this becomes the invalid `IN ()`, a SQLite syntax error. Research with every opt-in toggle off produces exactly that (no default entities at all, unlike every other non-Brainstorm chat type, matching §6's "Outline/chapters OFF, Full manuscript RAG OFF"). Guarded in `getChatContext` (`entityTypes.length > 0` added to the existing `chat.storyId ? search(...) : []` conditional) rather than inside `hybridSearch` itself — smaller blast radius, and every other caller already always passes a non-empty array so the bug was previously unreachable.

**S0's Story mode reuses `OutlineChatRail.tsx`'s exact most-recent-or-create pattern — no new server route.** `createGenericChat`/`useChatsByStoryQuery` already accepted `chatType: "research"` with a real `storyId` (confirmed via exploration before writing any code); the only genuinely new client-side piece is `ResearchTool.tsx`'s mode toggle (`Tabs` from `@/components/ui/tabs`, same component `CodexProposalTray.tsx` already uses for its pending/approved/rejected tabs) switching between that per-story chat and the pre-existing `getOrCreateGlobal("research", "Research")` single global chat — two independent single-chat identities, never a chat list (Research isn't Outline/WB's multi-chat rail). Mode defaults to Story when a story is active, forced to Global otherwise (with an effect resetting to Global if the active story clears while Research is open). `LorebookProvider`'s `storyId` prop and `ChatInterface`'s `storyId` prop both follow the same mode switch.

**S3 (save-as-note, note-proposal) required almost no new code — both fell into place from S0/S1's fixes.** `ChatMessageList`'s `onSaveAsNote` gate (`!isEditorChat && storyId ? ... : undefined`) was already correct; it was hidden for Research purely because `storyId` was always `undefined` pre-S0. Once Story mode supplies a real `storyId`, the exact same pre-existing gate starts working with zero changes — and stays correctly hidden in Global mode (no story to save a note against, which is correct behavior, not a residual bug). `note-proposal` was, ironically, already accidentally enabled via the `WORLDBUILDING_FRAMING` leak S1 fixed — `RESEARCH_FRAMING` keeps it deliberately rather than removing it, just adds the "on request" framing.

**S2 (citations) needed zero new rendering components.** `RESEARCH_FRAMING` instructs the model to cite via real markdown links (`[title](url)`); `MarkdownRenderer.tsx` (used by every chat message via `AssistantMessageContent.tsx`) already renders these as clickable `<a>` tags through `react-markdown` + `rehypeSanitize`'s default schema. The one small addition — a `target="_blank" rel="noopener noreferrer"` override on the `a` component — applies app-wide (notes, every chat type's messages), not just Research; a strictly-better UX fix piggybacked onto this pass rather than a Research-specific component.

**S5's Copy button is self-contained, unlike `onSaveAsNote`.** `ChatMessageList.tsx` gained a new `enableCopy?: boolean` prop rendering a hover-action `Copy` button (same `absolute opacity-0 group-hover:opacity-100` row as the existing `TtsPlayButton`/`onSaveAsNote` buttons) that calls `navigator.clipboard.writeText` + a toast directly — no callback threaded up to the parent, since clipboard writes need no shared state, unlike note-saving which needs the parent's `NoteFormDialog`.

Verified live via the boot log: `"Patched stale system prompt content for promptType 'research'"` on first restart after the fix, confirmed absent on a second restart (idempotent). **Split-dump and promote both landed on the existing `brainstormChecklist` table/pipeline, confirmed reusable before writing any new persistence code.** The second exploration pass confirmed the table (`chatId` FK → the generic `aiChats`, not a Brainstorm-only table), its service (`brainstormChecklistService.ts` — every function takes a plain `chatId`/`storyId`, no Brainstorm-specific logic anywhere), and its route (`server/routes/brainstorm.ts` — validates only that `kind` is in an allowlist, never checks the calling chat's `chatType`) all have **zero** chatType enforcement. This meant:
